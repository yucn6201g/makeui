# MakeUI - システム設計書

## 1. システム概要

MakeUI は、自然言語プロンプトから動作するUIモックを生成する AI アプリケーションです。
出力は TypeScript プロジェクトで、React / Vue / Svelte から選べます。

ジョブ実行の本体は **Amazon Bedrock AgentCore Runtime** 上で動きます。デザイン設計フェーズは
**Strands Agents SDK の Graph**（ルータが選んだ専門家の実行と、critic による仕様の編集）で構成し、コード生成は
`InvokeModelWithResponseStream` によるストリーミングで、推論と応答をチャットに逐次表示します。
API Lambda は認証・検証・ジョブ登録のみを担う薄い前段で、LLM は呼びません。

### 主要機能

- 自然言語から UI 生成（非同期ジョブ + ポーリング + ストリーミング表示）
- 出力形式の選択（React / Vue / Svelte のプロジェクト）
- モードの選択（下書き / 仕上げ / プラン）— 検査工程（設計グラフ・ブラウザ検証・修復・視覚批評）を走らせるかどうか。**モデルは決めない**
- マルチエージェント設計フェーズ（Strands Graph + Agents-as-Tools による KB 参照）
- 参照画像からの UI 生成・修正（生成 / 編集 / プランのいずれでも添付でき、設計とコード生成の両方に渡る）
- 生成済み UI の対話的修正（要素選択・画面追加対応。プロジェクトはファイル単位で編集）
- **要件の照合** — 依頼文から抜き出した要件（文言・表示場所・キー操作・画面）を完成物で確かめ、返答と修復に使う（2026-09-13〜）
- プロンプトの添削（Haiku による依頼文の具体化）
- デザインシステム RAG 検索（Bedrock Knowledge Base。独自デザインシステムの取り込みは削除済み）
- 品質スコアリング + プリセット準拠の機械検査・補正パス
- バージョン履歴の保存・参照（チャット履歴ごと復元）
- HTML 公開（30日間有効URL発行）
- 推論の停止と、生成中に離脱しても戻れば復元される再アタッチ
- Cognito MFA 必須認証 + 管理者パネル（使用量・モデル別の構成と使用量・ユーザー管理・プロジェクトとバージョン・グループ）
- トークン使用量追跡 + レート制限（台帳が読めないときは通さない — §5.5）
- プロジェクト選択時のプレビュー・プリセット・モデル・チャット履歴の復元、Untitled の自動命名、一括アーカイブ／削除
- プロジェクト一式の ZIP 書き出し（Vite スキャフォールド込みで、展開すれば動く）
- コードエディタ: プロジェクト全体の検索、Markdown プレビュー、ファイル単位の編集と保存
- ブラウザ実物のプレビュー枠（Chrome）とエディタ枠（VS Code）

### 2.1 実行系を Runtime に置いた理由

| | worker Lambda | AgentCore Runtime |
|---|---|---|
| 実行時間上限 | 900秒（固定） | セッション最長8時間 |
| 同時実行の分離 | 関数の同時実行枠を共有 | ジョブごとに専用 microVM |
| マルチエージェント | 900秒制約で設計グラフを載せられない | 設計グラフ + コード生成を同一セッションで実行可能 |

React のマルチ画面プロジェクトは設計フェーズだけで 60〜260秒かかります。Lambda では設計を厚くするほどコード生成の時間が枯渇するため、設計フェーズを単一呼び出しに留めざるを得ませんでした。

### 2.2 なぜ `/invocations` は 202 を即返すのか

`InvokeAgentRuntime` は同期 API で、応答は15分以内に返す必要があります。これは Lambda の 900 秒とほぼ同じ制約であり、「呼び出しの中でジョブを完走させる」設計では移設の意味がありません。

そこで `/invocations` はジョブをスケジュールしてすぐ 202 を返し、実処理はセッション内で走り続けます。進捗と結果は DynamoDB のジョブレコードに書かれ、クライアントは従来どおりそれをポーリングします。

ただしセッションには `idleRuntimeSessionTimeout = 900秒` があり、分離実行中は「無通信」と見なされて回収される恐れがあります。`GET /jobs/:id` の処理ついでに 120 秒に1回 `{"ping":true}` を同一セッションへ送ることで、クライアントの2秒ポーリングをそのままハートビートにしています。

### 2.3 縮退設計

`dispatchJob()` は Runtime 呼び出しに失敗した場合のみ worker Lambda に落とします。Runtime 障害時は旧来の 900 秒パスに縮退するだけで、リクエスト自体は失敗しません。`runJob()` の実装は両者で共有されているため、実行系が変わっても挙動は変わりません。

> この共有は事故を踏まえた設計です。以前は同じ処理が API 側と worker 側に二重に存在し、デプロイが片方だけに当たった結果、worker が2日間古いままストリーミング・プリセット・React 出力がすべて無効化されていました。

## 3. パイプライン設計

### 3.0 モードによる工程の取捨（config/effort.ts）

高価な工程は4つ — 設計グラフ、KB検索、ブラウザ実行検証、修復ループ。モードは、検査工程を走らせるかどうかを決めます。

| モード | 設計グラフ | ファイル単位ビルド | KB | 検証 | 修復 | 視覚批評 | 写真 |
|--------|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| `draft` 下書き | — | — | ✅ | — | 0 | — | 5 |
| `checked` 仕上げ（既定） | ✅ | — | ✅ | ✅ | 3 | ✅ | 5 |

**モードはモデルを決めません。** モデルはピッカー（`auto` ならルータ）が決め、管理者の許可集合で最後にクランプします。
旧4モード（`economy` / `fast` / `standard` / `thinking`）の値は `draft` / `checked` に読み替えて受け付けます
（保存済みのジョブや古いタブのため）。以下の表と記述は、4モードだった時期の設計判断と実測の記録です。

> **4モード時代の表（履歴）**
>
> | モード | 設計グラフ | ファイル単位ビルド | KB | 検証 | 修復 | 視覚批評 | 画像 | モデル |
> |--------|:---:|:---:|:---:|:---:|:---:|:---:|:---:|---|
> | `economy` 節約 | — | — | — | — | 0 | — | 3 | Haiku 固定 |
> | `fast` 高速 | — | — | ✅ | — | 0 | — | 5 | Sonnet 固定 |
> | `standard` 構築 | ✅ | — | ✅ | ✅ | 3 | ✅ | 5 | 選べる（`auto` ならルータ） |
> | `thinking` 思考 | ✅ | ✅ | ✅ | ✅ | 5 | ✅ | 10 | Opus 固定 |
>
> 「費用を名乗るモードがモデルを固定する」設計は、1つの決定に2つのコントロールを持たせ、
> 検査の有無とモデルという2つの軸を1つのダイヤルに載せていたため、2モードへの統合でやめました。

**（履歴）ファイル単位ビルドを `thinking` だけにしていたのは費用の判断でした（現在はどのモードでも使いません）。** 静的指標では全面的に上回りました
（CSS規則155対10、インラインスタイルではなくクラス、本物のSVGアイコン、空状態）。しかし1ラウンド
**400k〜1.1M トークン**で、単発呼び出しのおよそ3倍かかります。契約が全ファイルに付いて回るためで、
1プロジェクト中央値28ファイルなら28回travelします。一晩に十数回生成しただけで日次 Bedrock 枠を
使い切りました。

- 表を1箇所に置いているのは、モードの費用が個々のスイッチではなく**組み合わせ**だからです。ボタンに書いた約束と突き合わせて読めます。
- 環境変数（`DESIGN_SWARM_ENABLED` / `BROWSER_VERIFY_ENABLED`）は別ゲートとして残します。「この配備で何ができるか」と「この依頼が何を望むか」は別の問いで、両方が許可した工程だけが走ります。
- **（履歴）費用を名乗る3つのモードはモデルを固定していました。** 以前は `auto` のときだけ答え、明示選択を尊重していました。理屈は「上書きしたらプルダウンが嘘になる」で正しいのですが、結果として**節約 + Opus が Opus で走りました** — 約束は全部守ったうえで、いちばん高いモデルで。**費用を名乗るモードが費用の最大項を決められていない**。そこでメニューの方を変え、上書きではなく選べなくしました。
- 当時の固定は `modelForRun(effort, chosen)` の1関数で、**生成と編集の両方**が通ります。編集経路は以前 `browserVerify` だけをプロファイルから読んでいたため、**節約の編集が指示文ルーターに回って Opus を引くことがありました**。メニューのロックは利便性で、強制はサーバー側です（古いタブ・再開されたジョブ・直接呼び出しはメニューを通りません）。**管理者の許可集合は最後に必ずクランプ**します。
- 未知の `effort` は API が 400 で拒否します（`effort must be "draft" or "checked"`。旧4モード名は読み替えて受け付ける）。既定に落とすと、安いモードを選んだ人にフルパイプラインを課金することになります。

> **スコアは検証の有無で尺度が変わります。** ブラウザ計測が無いと実行時の減点（死んだ操作・空の枠・到達不能な画面・コントラスト・モバイル溢れ）が1つも入りません。同一依頼・同一モデル（Haiku）の実測で **節約 89（静的のみ）/ 構築 73（検証あり）**（現在の下書き／仕上げに相当）。節約が良いのではなく調べていないだけです。`metadata.scoreVerified` を返し、UI は「静的のみ」と明示します。

**実測（同一依頼・Haiku 固定・逐次実行）:**

| | 入力 | 出力 | 合計 | 所要 |
|---|---:|---:|---:|---:|
| 節約 | 20,156 | 43,765 | **63,921** | 4分09秒 |
| 構築 | 80,781 | 51,627 | **132,408** | 4分40秒 |

構築は節約の **2.1倍**。差の大半は**入力**（4倍）で、これが設計グラフと修復の入力です。

> 旧計測ではこの同じ比較が「節約 65,943 / 構築 59,810」— **節約のほうが高い**と出ていました。文字数を4で割っていたため、測っていたのは HTML の大きさで、仕事の量ではなかったからです。詳細は §3.0.1。

### 3.0.1 トークン計測（services/token-ledger.ts）

以前は `Math.ceil(text.length / 4)` を7箇所に置いた推定でした。2つの取りこぼしがあります:

1. **4エージェントの設計フェーズが1トークンも計上されていませんでした。** `runDesignSwarm` は文字列を返すので、グラフの usage メトリクスは中で捨てられていました。パイプライン最大の工程が無料に見えていたわけです。
2. 修復パスは**生成した文書の長さ**だけを数え、入力を数えていませんでした。

   （当時の記述は「ファイルごとにプロジェクト全体」でしたが、これは現在の実装には当てはまりません。
   ファイル単位の修復が送るのはそのファイルの中身と欠陥だけで、プロジェクト全体ではありません。）

つまり**節約・高速が省く工程が、そもそも計上されていない工程**でした。だからモードを変えても使用量がほとんど動かなかったのです。

いまは AsyncLocalStorage の台帳に、各呼び出しが**モデルの申告値**を入れます。呼び出し側に何も引き回さないので、新しい呼び出しが計上漏れになりにくい形です。

台帳は**段階ごと**に割れます。合計は「いくらかかったか」しか答えず、次に来る問いは必ず
「どこで使ったか」だからです。ラベルを付け忘れた呼び出しは `unattributed` として残り、
消えません。設計フェーズが無料に見えていた事故は「見えない欠落」だったので、欠落は見える
形にしてあります。

Bedrock が返す `cache_read_input_tokens` / `cache_creation_input_tokens` も同時に記録します。
**効いていないプロンプトキャッシュは無言で失敗する**ためです — モデルの最小長を下回るか、
前置きが1バイトでも動けば、エラーも警告もなく `cacheRead: 0` のまま満額課金されます。

**実測（`standard`・Haiku・会議室予約のブリーフ・3ラウンド）:**

| 段階 | 呼び出し | 割合 |
|---|---:|---:|
| `repair:per-file` | 78 | 37% |
| `build:single-call` | 3 | 27% |
| `design:*`（4ノード合計） | 12 | 28% |
| `critic:visual` ほか | 15 | 8% |

設計グラフは style-expert / interaction-designer / content-strategist が各8〜9%、
layout-architect が3%で、**切るべき突出したノードはありません**。

### 3.0.2 プロンプトキャッシュが効かない理由（実測）

Bedrock でプロンプトキャッシュは GA で、この呼び出し経路でも動きます（21,600トークンを
書き、次の呼び出しで読み戻すことを確認済み）。**最小長は実測で 3,531〜4,411 の間**
（Haiku 4.5 の文書値 4,096 と一致）。下回ると書き込み0・読み込み0・エラーなしです。

それでも3箇所すべてで成立しませんでした:

| 対象 | 理由 |
|---|---|
| `standard` | 繰り返す前置きが存在しない（ビルドは単発呼び出し1回） |
| `repair:per-file` | system プロンプトが219トークンで、閾値の5% |
| `build:per-file` | 前置きが**設計上**毎回変わる |

最後のものは実装して測りました。1ラウンドで **cacheWrite 123,183 / cacheRead 0** —
1.25倍の割増だけを払う形です。原因は `landed` が波の途中で増えることで、sibling と
コンポーネント署名がそこから読まれます。これは「後から書く画面が実物の部品を見る」ための
意図的な仕組みで、そのぶん前置きが安定しません。増える部分を後ろに逃がすと、残る固定部は
約3,000トークンで**今度は閾値を下回ります**。

**この形のパイプラインでは、プロンプトキャッシュはレバーになりません。**

- **モジュール変数ではなく AsyncLocalStorage** — worker Lambda は1プロセスで2ジョブを持てるので、共有カウンタだと互いの分を請求し合います。
- **申告の無い呼び出しは「推定」ではなく「欠落」として数えます**（`unreported`）。実数の合計に推測を混ぜると下流が区別できません。欠落が見えることが、設計フェーズの取りこぼしを早く見つける唯一の手段でした。
- ストリーミングは `message_start`（入力）と最後の `message_delta`（出力）の**両方**を読みます。片方だけだとゼロ計上になります。
- 旧 `services/token-tracker.ts` は使われなくなったので削除しました。

### 3.0.2 Bedrock 呼び出しのタイムアウト（config/bedrock-client.ts）

`BedrockRuntimeClient` を4モジュールがそれぞれ生成しており、**どれもタイムアウト無し**でした（SDK 既定は無制限）。実測: `preset-conformance` に入って1回呼び出し、**32分間ジョブレコードが1度も更新されず**、エラーも出ず、何も書かれませんでした。クライアントのポーリング上限は16分なので、ユーザーには「終わらない生成」に見えます。

クライアント生成を1箇所に集約し、`requestTimeout` を **10分**にしました。観測された最長の正常呼び出し（マルチ画面 React の組み立て、5分30秒）の約2倍で、修復予算20分の半分です。上限は**正常な呼び出しより上**に置く必要があります — 遅いビルドを失敗に変えてしまうからです。`connectionTimeout` は10秒（接続できないことが「遅いが正常」であることはありません）。

### 3.0.3 添付データ（utils/data-attachment.ts）

CSV・TSV・JSON・Markdown・テキスト・PDF を、生成・プラン・編集のどれにも添付できます。**蒸留が本体**であって、サイズ制限のおまけではありません。

ユーザーは手元のファイルをそのまま添付します。モデルが必要なのは**形と、それらしい十数件**だけで、全件を送ればビルド本体より高くつき、先頭12行以上のことは何も教えません。だからコード側で読み、**ヘッダ＋12行と実件数**だけがプロンプトに載ります。

| | 実測 |
|---|---|
| ファイル | 205,925文字（3,847行） |
| プロンプトに載る量 | **948文字 ≈ 430トークン** |
| 生成1回の総量 | 約270,000トークン |
| 添加率 | **0.16%** |

行の分割は**引用符を尊重**します。住所や備考の改行こそが「本物に見えるデータ」を作る列で、`split('
')` はそこで壊れます。

**実件数を抜粋の隣に書く**のは、両方が別のことを言うからです。抜粋は「1レコードがどう見えるか」、件数は「画面が何件を捌くか」。6行のリストと4,000行のリストは別の設計（検索・絞り込み・ページング）で、件数がなければモデルは常に前者を作ります。だから**設計フェーズにも渡します** — ビルドにだけ渡すと、6行用の画面が本物の値で埋まって返ってきます。正しく見えて、画面が違う。

PDF は**ブラウザ側でテキストに変換**して送ります。抽出後は既存のテキスト添付経路に乗るので、API・ペイロード・蒸留は一切変わりません。実測: 2ページの日本語ガイドラインで263文字、日本語もヘックス値も無傷。ただし表は `商品コード 商品名 在庫数` と1行に潰れるため、**資料であってデータ源ではありません**（`attachmentKind` は `.pdf` を markdown 系に落とします）。テキスト層のないPDFは**添付を拒否**します — 空の添付は「添付なし」と区別がつかず、生成が返ってきて初めて無視されたと分かるからです。

#### 編集への配線（実測で1度落とした）

`dataContext` は `changeSpec` に混ぜてはいけません。`changeSpec` は書き換え側に「インタラクションデザイナーが仕様化した」として提示されるものであり、かつ**ルーターが設計パスを要求したときしか作られません**。実測: 「モックデータを添付CSVに差し替えて」は `needsDesignPass: false` と判定されます — この機能が一番必要な編集でちょうど落ちます。

初回の実機検証で**データは1件も届きませんでした**。全レイヤーを配線したのに、`runModify` が `directModify` を11引数で呼び、12番目がデータでした。`dataContext` を**オプショナルかつ末尾**にしたのが原因で、**TypeScript は省略されたオプショナル引数を検出できません**。型もテストも通り、実機で初めて分かりました。

現在は3つの関数（`directModify` / `fullHtmlModify` / `projectFileModify`）すべてで**必須引数**とし、オプショナル群の前に置いています。データを渡してはいけない箇所（品質修復の「この点だけ直して」呼び出し）は**明示的に `''`** と書きます。以前は「何も書かない」で、それがバグと同じ見た目でした。

### 3.1.1 Swarm 実装上の制約（実機検証で判明）

> 設計フェーズは、実行順がモデル任せで仕様の長さが大きく揺れたため Swarm から Graph に移しました。
> 以下は Swarm 時代に判明した制約の記録で、ノードの一意な `id` とトークン上限は Graph でも同じです。

TypeScript 版 Strands SDK（当時 v1.11.2）が提供するのは `Agent` / `Swarm` / `Graph` / `tool` で、**`Workflow` と `A2A` は存在しません**（Python 版のみ）。Python を使わない方針のため、この2パターンは採用していません。

| 事象 | 原因と対処 |
|------|-----------|
| `duplicate agent id` で失敗 | ノードには一意な `id` が必須。`name` だけでは足りない |
| 成果物が108文字しか取れない | Swarm はハンドオフを structured output で行う。成果物は `NodeResult.content` ではなく `structuredOutput.message` に入り、`content` には前置きしか入らない。全ノードの `structuredOutput.message` を連結して取り出す |
| `Model reached maximum token limit` | ハンドオフ自体がトークンを消費する。`maxTokens: 8000` では落ちるため 32,000 を設定 |

### 3.1.2 ストリーミングと推論・応答の分離

生成中は 900ms ごとに `streamTail` / `streamChars` をジョブレコードへ書き込みます。出力の先頭に本文以外の散文があれば、それを「計画（推論）」として切り出します。

```typescript
const docStart = cleanedHtml.search(/<!DOCTYPE html|<html[\s>]/i)
const plan = docStart > 0 ? stripFences(cleanedHtml.slice(0, docStart)) : ''
```

`stripFences()` は先頭に限らず文書中のどこにあるマークダウンフェンスも除去します。

| outputKind | エントリ | 拡張子 |
|-----------|---------|--------|
| `react` | `src/main.tsx` | `.tsx` / `.ts` |

### 3.1.4 文書形式（転送）

複数ファイルのプロジェクトは1つの文字列として運ばれます。形式は行フェンスです:

```text
@@@makeui:file src/App.vue
<template>…</template>
<script setup lang="ts">…</script>
@@@makeui:endfile
```

以前の `<script type="text/jsx" data-file="…">` 形式は、**運ぶ言語と衝突します**。React のソースが `</script>` を含むことは稀ですが、Vue と Svelte の単一ファイルコンポーネントは**必ず**自分の `<script>` を持ちます。最小の SFC で実測：113 バイト書き込み、68 バイト読み出し、`<style>` ブロックと閉じタグが消失。読み手の不具合ではなく形式の問題で、内側からのエスケープでは直りません。

読み手は**両形式を解釈します**。新規プロジェクトはフェンス形式、既存の16件の React プロジェクトは旧形式のまま読めます。書き換えは途中で失敗しうる移行作業であり、読み手が読み続けられる形式を引退させるためにそれを行う理由がありません。

### 3.1.5 生成物の静的検査（フレームワーク固有）

ブラウザ検証は `checked`（仕上げ）でしか走りません。`draft`（下書き）は `repairPasses: 0` でもあるため、**安全網が無い状態で出荷されます**。そこで、描画せずに機械判定できる不具合は静的に見ます。

| 検査 | 何を捕まえるか | なぜ他では見えないか |
|------|--------------|-------------------|
| `component-unresolved` | どこからも import されていないコンポーネント | **コンパイルが通り、描画もされる**。要素が不活性になるだけ。実測：`<router-link>` を並べたサイドバーで、9個中8個のコントロールが死に、ハッシュは一度も変わらず、7画面中1画面しか到達できなかった。エラーは1件も出ていない |
| `svelte-legacy-idiom` | Svelte 4 の `export let` / `on:` / `<slot />` が混在 | コンパイラは報告するがパーサ位置として報告する。実測：`Unexpected keyword 'class'` — 本当の問題は「props を Svelte 4 の書き方で書いた」ことだった。位置を渡された修復は1行を直し、イディオムを渡された修復は宣言を書き直せる |

決定論的な書き換えはもう1つあります。`$derived(() => {…})()` → `$derived.by(() => {…})`（`normalizeSvelteRunes`）。Svelte 5 の `$derived` は式用、`$derived.by` は文を含む計算用で、モデルは存在しない第3の形（関数を呼んで値を得る）を書きます。ルーン自身が初期化子で**なければならない**のに、そこでの初期化子は呼び出し式になるため拒否されます。`$derived.by(fn)` は IIFE が意図していたものそのものなので、これは修復ではなく改名です。呼び出しの終端は正規表現ではなく括弧の対応を数えて求めます（本体は任意のコードで、文字列リテラルの中に括弧が入りうるため）。

**フレームワークによって「何がエラーか」が違う** ことは、生成規約の側で吸収します。同じ生成物が React と Vue では描画され、Svelte ではビルドごと止まる、ということが実際に起きます。実測した2件:

- Svelte は `<button>` の中の `<button>` を**コンパイルエラー**にします（警告ではありません）。カード全体を巨大な `<button>` にして中に「借りる」ボタンを置いた生成物が、`<button> cannot be a descendant of <button>` でプロジェクトごとビルド不能になりました。規約側で、クリック可能なカードは `<div onclick role="button" tabindex="0">` と書くよう指示しています。
- 逆に Vue のテンプレートコンパイラはほぼ何からでも回復します。壊したテンプレート5種（解析不能な補間・途中で切れた `v-for`・閉じていないタグ・途中で切れたハンドラ・途中で切れた `v-if`）を与えて、エラー5件・**描画関数5件**が返りました。だから `template.errors` を致命扱いにしてはいけません（3.1.3 の脚注参照）。

さらに `<router-link>` → `<a href>` は**決定論的に書き換えます**（`normalizeRouterLinks`）。モデルに直させるのではないのは、書き換えが機械的であり、かつ修復パスを持たないモードでは「検出したが直さない」＝「壊れたまま出荷」になるためです。実測、同一プロジェクトのブラウザ計測:

```text
        死んだコントロール   到達画面   変化したルート
before      9個中8個          1          なし
after       9個中3個          7          6
```

残る3個は正しい挙動です（ホーム表示中の「ホーム」、件数バッジ、フィルタのクリア）。

### 3.1.6 プリセット準拠の機械検査

`PRESET_SIGNATURE` に必須値（required）と禁止パターン（forbidden）を持たせ、生成物を機械的に検査します。適合率が 75% 未満、または違反が1件でもある場合のみ補正パスを1回実行し、**補正結果は計測上改善した場合のみ採用**します。

### 3.2 プリセット仕様（PRESET_SPECS）

`graph.ts` 内の `PRESET_SPECS` 辞書にプリセット別のデザイントークンを直接定義しています。プリセット `"none"` の場合は組み込みデザインシステムを適用します。

### 3.4 fullHtmlModify（meta-orchestrator.ts）

`POST /modify` で使用。**プロジェクト（React / Vue / Svelte）で画像の添付が無い編集は、まずファイル単位の編集
（`projectFileModify`）で行い**、それが降りたときや単一ページのときに、ストリーミングで文書全体を変換します。
どちらの経路も最後に決定的修復をかけ、編集が持ち込んだ不備と、要件の照合で漏れた指示を1回修正します
（ビルドが通らなくなった修正は採用しない）。流れの全体は `04_backend.md` の「修正パイプライン」。

```typescript
async function fullHtmlModify(
  html: string,
  instruction: string,
  modelId: string,
  maxTokens: number,                   // 64000 固定
  preset?: string,
  onDelta?: (chunk: string) => void,   // 逐次表示
  onPlan?: (plan: string) => void,     // 本文前の散文を推論として分離
): Promise<string>
```

- 変換に失敗した場合は**診断メッセージ付きで例外を投げます**。入力をそのまま返して「成功」に見せることはしません
- React プロジェクトには `REACT_MODIFY_GUARD` を前置し、ブロック構造・TypeScript・フォルダ構成の維持を強制します
- バージョン履歴にはガード文を含まないユーザー自身の指示を保存します

**出力トークン上限の履歴**: 以前は `model === 'haiku' ? 8000 : 64000` でした。Haiku で「画面を追加して」と指示すると出力が途中で切れ、「変更を適用できませんでした」になっていました。現在は全ティア 64000 です。

**設計判断**: HTML→HTML の変換は単一の原子的操作です。以前の Strands Agents-as-Tools 構成では、各スペシャリストツールが CSS や JSON の断片を返していたため、結合時に常に元の HTML と同一になっていました。設計フェーズ（発散的で並行化の価値が高い）にはマルチエージェントが効きますが、変換フェーズには効きません。

**ただし React プロジェクトは別です**（`edit-files.ts`）。原子的なのは HTML 文書のときだけで、
生成される React プロジェクトは30ファイル・80KB あります。「レポート画面を追加して」に対して
変更対象でない30ファイルを書き直させることになり、出力 25〜32k トークン、文書が大きいほど
途中で切れる確率が上がる — 構造的な変更がこの製品への定常的な苦情だった原因はこの形です。

安い1回の呼び出しでファイル一覧と指示だけを見せて対象ファイルを決め、その後は1ファイル1呼び出し。
1ファイルはモデルが正しく返せる単位で、呼び出しは独立なので並行に走ります。
生成側の修復で先に実測した形（9ファイル 19.6秒 対 全文1回 約150秒）をそのまま持ってきています。

聞かずにこちらで決めることが2つあります。どちらもモデルが忘れると
「適用されたように見えて適用されていない」変更になるためです。

- **新しい画面はルーティングを連れて行く。** 画面ファイルだけ作ってルートに登録しないと、
  ファイルは存在しコンパイルも通り、どこからも開けない画面ができます。
  検証は `screen-unreachable` と呼び、利用者は「画面が追加されていない」と言います
- **ルーティングの編集が返ってこなかったら、新しい画面ごと捨てる。**
  到達できない画面を「成功しました」と報告するのは、何も変えないより悪い結果です
- **利用者が押すと言ったコントロールも計画に入れる。** 実測:
  「お問い合わせのリンクを押したときに表示されるお問い合わせページを作成して」に対し、
  画面・ルート・App の分岐は全部正しく作られ、`<a href="#">お問い合わせ</a>` は
  そのままでした。`href="#"` はどこにも行かないリンクで、その表示ラベルが指示に
  出てくるなら、それが入口です
- **画面が返ってこなかったら、そのために計画した全部を捨てる。** 実測:
  ContactScreen が落ちたのに routes.ts とフッターのリンクだけ着地し、
  押すと何も描画されないルートに飛ぶ状態になりました。半分の変更は小さい変更ではありません
- **配線の手段はプロジェクト自身のコードから引用して渡す。** 実測: Footer が
  `../hooks/useNavigate`（React Router の名前）を import して差し戻されました。
  説明より、実物の1行のほうが確実です

**ゲートは差し戻しの「後」に問う。** import 検査を差し戻し前に走らせていたため、
パースできない ContactScreen がまだ文書内にあり import は解決し、その後で画面だけ
消えて App.tsx が幽霊を import した状態で出荷されました
（`Module not found: './screens/ContactScreen'` → 白紙）。
ゲートは**出荷される文書**に対して問わなければ、下書きに対するゲートです。

**モデルの応答から転送ブロックを剥がす。** `reactFiles` はブロックを、それを開いた
タグに対応する閉じタグまでしか読みません。モデルが `<script data-file=…>` ごと返すと、
事前検査は完全な本文を見て通り、埋め込み後は切り詰められた断片が入ります
（実測: 245行目で切れた）。`test/splice-roundtrip.test.mjs` で往復の性質を固定しています。

**閉じタグは「開いたタグ」と対応させる。** ここは長らく `</script>` と `</style>` の
どちらでも — どちらが開いたかに関係なく — ブロックを終わらせていました。JSX の中で
style 要素を描く画面は普通の React ですが、この読み取りではその内側の `</style>` で
ファイルが切れます。実測: 出荷済みプロジェクトの 6.8KB の ProductDetailScreen.tsx が
3.0KB として読まれ、JSX の途中で終わってパースできませんでした。
**下流のすべて** — 監査・修復プランナ・スコア — が、文書に実在しない「半分のファイル」を
見ていたことになります。ブラウザ側のプレビューは同じバイト列を DOM 自身のパーサで読むため
（script は `</script>` でしか閉じない）、両者はプロジェクトが**何であるか**について
食い違っていました。正規表現の後方参照でタグ名を対応させて解消。
あわせて `writeFile` の拒否条件も転送に合わせています（CSS は `</style>`、それ以外は
`</script>`。両方を両方に対して拒否するのは、起こり得ない切り詰めを避けるために
正しい修復を捨てる方向に厳しすぎました）。

> この2つは同じ1プロジェクトから出てきました。ユーザーに見えたエラーは
> AppProvider.tsx の引用符欠落だけですが、実際には**2ファイルが壊れて**おり、
> 単一エラーの経路では最初の1つしか出せません。`syntaxDefects()` はファイル単位で
> 報告するので、両方が同時に出ます。

画像を要求する指示（写真・画像・photo…）には、ストック画像の実URLを渡します。
以前は生成時にしか渡していなかったため、「商品の写真を入れて」の答えは
グレーの箱か、404 になる捏造URLでした。

### 3.4.0 複数の要求を含む指示

「在庫画面を追加して、遷移も付けて、ボタンの色も変えて、CSVエクスポートも」のような指示は、**全工程で1つのこととして扱われていました** ── scope 1つ、`changeSpec` 1つ、ファイル計画1回、そして**各ファイルが指示文の全体を読む**（色トークンを直すだけのファイルも「CSVエクスポートを付けて」を読む）。

そして決定的に、**指示が実行されたかを誰も検査していませんでした**。編集後に走るのは全部「この編集が新たに壊したもの」の検査（`auditAiTells` の差分、`moduleDefects` の差分、ブラウザ検証）なので、**4件中2件しか実装されなくても「新しい欠陥ゼロ・ブラウザ clean・成功」**として返ります。

#### B: カバレッジを報告する（`describeEditOutcome`）

`applyFileEdits` は既に `written` と `skipped` を返しており、`plan.reason` は各ファイルの役割を計画側の言葉で持っています。情報は揃っていて、**ログにしか出していませんでした**。

編集前に出した計画を、**結果で上書き**します:

```
✓ 新規 src/screens/Inventory.tsx — 在庫管理画面を追加
✓ 編集 src/routes.tsx — ダッシュボードからの遷移
✓ 編集 src/styles/tokens.css — ボタンをブランドカラーに
× 新規 src/lib/export.ts — CSVエクスポート（適用できませんでした）
```

「計画されたのに書かれなかった」を未適用とします。`skipped` だけを信じると、パースできない返答・適用できない splice・短すぎる本体など**別経路で落ちたファイルが「完了」と表示されます**。

#### A: 指示を部分に分解して持ち回る

ルーターの戻り値に `parts` を足しました。**モデル呼び出しは増えません** ── 同じ分類呼び出しが、同じ文を読んで分解も返すだけです。

- 部分は**番号付きでファイル計画に渡り**、計画は各ファイルがどの番号を担当するかを返します
- 各ファイルには**自分の部分だけ**が「このファイルの担当」として渡ります（指示文全体は文脈として残ります）
- **対応が不明なファイルは絞り込みません。** 断片を間違って渡すほうが、多く渡すより悪いからです
- 1部分の指示は**分解前とバイト単位で同じプロンプト**を送ります

ルーターが壊れた応答を返した場合は「指示全体＝1部分」に退行します。**分解しないのは安全、間違った分解は危険**です。`ROUTER_MAX_TOKENS` は 400→900 に上げました（4部分の日本語＋JSON が 400 に入らず、切り詰められた応答は小さい答えではなく**パースできない JSON**だからです）。

#### C: 種類の異なる要求が混ざる指示は必ず設計パスを通す

`changeSpec` が**部分を各ファイルへ一貫して運ぶ唯一の経路**です。これがないと各ファイルは「指示文」と「自分の断片」を見るだけで、両者を関係づけるものがありません。

同じ種類の部分が複数（色を3箇所変える）では発火しません ── **仕様は要らず、編集が3回要るだけ**なので。**唯一トークンを消費する変更**です。

#### 実測（v242、Haiku、既存の React プロジェクト）

**4部分の指示**（画面追加＋遷移＋色＋CSV）:

```
66s | 91,276 → 96,133 chars | 38,465 tokens | 4/4 着地
✓ 新規 src/screens/FavoritesScreen.tsx — new favorites list screen
✓ 編集 src/routes.ts / src/App.tsx / src/store/types.ts / src/styles/globals.css
```

`#0F5C55` はモデルが自力で選ばない値なので、色の部分は偶然の一致ではありません。

**ただしこのラウンドは C を測れていません。** `scope: structural` は**元々無条件で設計パスを強制**するため、`needsDesignPass: true` は新しい規則の証拠になりません。

#### C の対照（visual と content だけ、structural を含まない）

```
45s | 26,275 tokens | 4/4 着地、新規ファイルなし
```

分解ログ:

```
parts: ["visual: 見出しのフォントサイズを大きくして",
        "visual: カード全体の余白を広げてください",
        "content: 商品名の表記を「商品名（税込）」の形式に統一し",
        "content: 商品が無いときのメッセージを「まだ商品がありません」に変更してください"]
```

ルーターを直接呼んで確定させました（生成ラウンドではなく分類呼び出し1回）:

| 指示 | parts | kinds | needsDesignPass | ルーター自身の理由 |
|---|---|---|---|---|
| visual 2 + content 2 | 4 | 2種 | **true** | 「いずれも既存機能内の変更であり**新たな設計は不要です**」 |
| visual だけ 3件 | 3 | 1種 | **false** | 「すべてがスタイル調整で…」 |
| 1件 | 1 | 1種 | false | — |

**1行目が C の証明**です。ルーター自身が「設計は不要」と言っているのに `true` になっているので、上書きしたのは `mixedKinds` 以外にありません。2行目が境界の証明で、**同種が複数でも発火しません**（仕様どおり）。

### 3.4.1 写真の割り当て（assign-images.ts）

生成・編集のどちらでも、**組み上がった後に**すべての写真を割り当て直します。実測した失敗:

```
name: 'オーガニックコットンTシャツ'  image: .../stock/office/35f3fd7a….jpg
name: 'ウールニットセーター'        image: .../stock/workspace/c327….webp
name: 'デニムジーンズ'              image: .../stock/office/4a2a….jpg
```

衣類3点にオフィスの写真2枚。URLは全部生きていて、マークアップも正しく、検査も全部通ります。
**見た目だけが間違っている** — 人が見ないと分からない種類の欠陥です。

原因は提示の形でした。組み立てモデルには画面ぶんのURLが数本渡され、画像が要る場所に
それを書きます。カタログを書いている時点で「どのURLが何の写真か」を知らないので、
モデル側でこれ以上うまくやる方法がありません。だから割り当てをモデルから取り上げ、
**商品1件ごとに、その商品の名前に対して**決めます。モデル呼び出しなし・決定論的。

ライブラリは**被写体**で引きます（`butter` / `tshirt` / `warehouse`）。以前の7分類は
`office` `people` `workspace` `city` `nature` `abstract` `product` で、`product` は
撮影できるものを指していないため事実上すべてに一致していました。

一致しなかったときは**写真を出しません**。近い写真を出すのが、Tシャツに机の写真が付く経路です。
中間の段として、被写体は分かったが在庫が無い場合だけカテゴリに落とします
（バターが無くてもチーズは「同じ種類のもの」の写真であり、コンクリート壁とは違う）。

用語表（`subject-terms.ts`）と収集対象（`scripts/subjects.mjs`）は別ファイルです。
写真が変わるのは再収集のときだけ、利用者が打つ言葉は常に変わるためで、
「バタ」を追加するのに600枚を再ダウンロードする必要はありません。
両者がずれていないことはテストで固定しています。

**枠だけ空けさせる（`__PHOTO__`）。** 実測: バター2枚を含む5本のURLを渡したところ、
組み立てモデルは商品8件のカタログを名前・価格・規格・オプションまで完備で書き、
**画像を1件も付けませんでした**。「写真は控えめに」と指示されており、それは
ダッシュボードには正しくショップには誤りです。そもそもモデルは5本のうちどれが
バターの写真かを知りません。

なので、モデルには確実にできることだけを頼みます — **枠を空け、品名を具体的に書く**。

```
{ id:'p1', name:'北海道産 無塩バター 200g', price:1280, image:'__PHOTO__' }
```

写真を選ぶのは後段の仕事です。トークンが残ったまま出荷されると全カードが画像切れに
なるため、ライブラリが読めなかった場合も含め、**必ず**プレースホルダに置換します。

ライブラリ: **3,239枚 / 115被写体**（旧 56枚 / 7分類）。空の被写体はゼロ、最小 5枚、中央値 32枚。
旧分類（office/ people/ nature/ …）に残っていた被写体タクソノミー以前の54枚は、
インデックス確定後に S3 キーとインデックスの差分を取って削除済みです。
`node scripts/curate-images.mjs --per-query 4` で再収集、`--skip-existing` で再開できます。

### 5.5 台帳が読めないときは通さない

支出ガードは3つあり、いずれも同じ DynamoDB テーブルを読む。読めなかった場合、
かつては3つとも「通す」と答えていた。**1回のテーブル障害で支出ガードが全部消える**
状態で、しかもその主因はスロットリング、つまり**負荷時に起きる**。守る対象と故障が
相関するものはガードではない。

| ガード | 読めないときの答え |
|---|---|
| `checkUsageLimit` | 拒否（`known: false`） |
| `checkRateLimit` | 拒否（`known: false`） |
| `getUserAllowedModels` | `null` → `allowedModelsForRun` が **haiku**（最も安い階層）に落とす |

呼び出し側は `known === false` を **HTTP 503 + `Retry-After`** に変える。403（上限超過）
でも 429（速すぎ）でもない ── どちらもその利用者についての主張で、読み取りが失敗した
ときには**誰も確かめていない**。

`getUserAllowedModels` だけ拒否ではなく降格なのは、これを読むのが AgentCore Runtime の
中、**ジョブが受理された後**だから。そこで断ると利用者はリクエストごと失う。haiku は
最も安い階層なので、落としても支出は増えない。

レートリミッタの `ConditionalCheckFailed` リトライ経路だけは今も通す ── そこは
**バケットを読めていて予算内であることも分かっており**、記録だけが競合で負けている。
過少計上であって素通りではない。

### 6.2 プレビュー iframe セキュリティ

```html
<iframe sandbox="allow-scripts" />
```

- `allow-scripts`: 生成された JS の実行を許可
- `allow-same-origin` は**付与しない**: オリジン分離を維持

**previewGuard.ts（`PREVIEW_GUARD_SCRIPT`）** を生成 HTML の `<head>` 直後に挿入して制御:

| 動作 | 詳細 |
|------|------|
| 外部URL ブロック | `https://` `//host` `mailto:` 等を preventDefault + トースト通知 |
| onclick 保全 | stopImmediatePropagation 不使用 → 全クリックハンドラーが正常動作 |
| 相対パスナビゲーション | anchor scroll にフォールバック。行き先が無ければ「この画面はまだ作られていません」 |
| ハッシュナビゲーション | **ガードが `location.hash` で実行する**（通過させない。理由は下記） |
| フォーム送信 | preventDefault + トースト表示 |
| window.open | noop（ポップアップ禁止） |
| リップルエフェクト | ボタン・リンクにビジュアルフィードバック追加 |
| ウォッチドッグへの応答 | `makeui-preview-ping` に pong を返す |

**ハッシュリンクを通過させてはいけません。** srcdoc 文書の URL は `about:srcdoc` ですが base URL はホストページから継承されるため、ブラウザは `#/cart` をホストに対して解決し、別文書とみなして**フル遷移**します。生成アプリはすべてハッシュでルーティングするので、画面遷移のリンクすべてがプレビューを壊していました（実測: `beforeunload` 発火 → `load` 発火 → フレーム応答なし）。`location.hash` への代入なら文書自身の URL に対する操作になり、同一文書のまま `hashchange` が発火します。

**`Location.prototype` の行は削除しました。** 効いていなかったからです。`href`/`assign`/`replace` は location オブジェクトの `[LegacyUnforgeable]` own プロパティで、prototype 側の再定義も代入も黙って失敗し、try/catch がそれを隠していました。中から防げないので、Preview.tsx のウォッチドッグが `load` ごとに ping を投げ、pong が返らなければ `srcdoc` を書き戻します（フレームは opaque origin なので location を読んで判定することはできません）。

### 6.3 追加バリデーション

| 対象 | バリデーション |
|------|-------------|
| `/publish` の page.id | `^[a-zA-Z0-9._-]+$` パターン検証（S3 パストラバーサル防止） |
| `/versions` の `html` | プロジェクト記録の `lastHtml` と同じ上限（350,000 バイト）。**文字数ではなくバイト数**で測ります |

### 8.3 React プロジェクトのブラウザ内実行（reactPreview.ts）

生成物が `<script type="text/jsx" data-file="...">` ブロック群の場合、バンドラを使わずブラウザ内で実行します。

```text
data-file ブロック群 → virtualFs.ts（仮想FS）→ transformsFor()
  → Sucrase（TS/JSX 変換）→ resolve()（import 解決）→ React ランタイムで実行
```

| 問題 | 対処 |
|------|------|
| `.ts` の `useRef<Route[]>` が JSX として解釈され失敗 | `transformsFor()` で拡張子ごとに変換を切替。`.tsx` のみ jsx 有効、`.ts` は typescript のみ（失敗時は `.tsx` として再試行し警告） |
| モデルが `../imports/icons` と階層を誤る | `resolve()` が完全一致で見つからない場合に末尾一致でフォールバック |
| 未解決 import が空オブジェクトになり白画面 | 解決できない import は**例外を投げるスタブ**に置換し、原因が見えるようにする |
| キャンセル時に `compiling` が残り永久に白画面 | 中断時も必ずフラグを解除 |

> SPA モードは削除されました。画面遷移はモード切替ではなく、生成そのものが複数画面とルーティングを含むかたちに置き換わっています。

## 10. モデル選択戦略

`resolveModel()` 関数（`model-config.ts`）が一元処理：

```typescript
export type ModelChoice = 'sonnet' | 'opus' | 'haiku' | 'auto';

export async function resolveModel(model?: ModelChoice): Promise<BedrockModelConfig> {
  if (!model || model === 'auto') return getDefaultModel();   // SSM /makeui/models/default を参照
  const tier = model === 'opus' ? 'quality' : model === 'haiku' ? 'lite' : 'fast';
  return getBedrockModel(tier);           // SSM /makeui/models/{name} を参照
}
```

| 選択 | tier | SSM パス | maxTokens | temperature |
|------|------|----------|-----------|-------------|
| `auto`（既定） | 依頼文から決定 | 選ばれたティアの SSM パス | 64,000 | 選ばれたティアに従う |
| `haiku` | lite | `/makeui/models/haiku` | 64,000 | 0.3 |
| `sonnet` | fast | `/makeui/models/sonnet` | 64,000 | 0.3 |
| `opus` | quality | `/makeui/models/opus` | 64,000 | 0.7 |
| 未指定 | SSM default | `/makeui/models/default` → tier | — | — |

> デフォルトモデルの変更は SSM パラメータ更新のみで反映（デプロイ不要、5分キャッシュ後に適用）。

### 自動（`auto`）

UI の既定値です。生成時のみ `resolveModelForPrompt(model, prompt)` を通り、**最も安い
Haiku を分類器として1回**呼んでティアを決めます。分類器が使えないときは
`fallbackModelSelection()` のキーワード規則に落ち、既定は sonnet です
（小さすぎるモデルを引くと作り直しになるが、大きすぎても費用しか失わないため）。

決定は `Auto-selected model` ログと `FinalOutput.metadata.autoModel` に残ります。

実測（2026-08-07、本番 Runtime v49）:

| 依頼 | 選択 |
|------|------|
| 「ざっくりでいいので、ログイン画面のモックを作って」 | `haiku` |
| 「カフェの予約サイトを作って。メニュー一覧と予約フォームと確認画面」 | `sonnet` |
| 「本番投入する社内の経費精算SaaSを作り込んで…クライアント提出品質で」 | `opus` |
| 「ボタンの色を変えたい」 | `haiku` |

> **Bedrock Intelligent Prompt Routing は 4.x 系モデルに未対応**のため使っていません。
> 詳細と検証手順は `04_backend.md` の「自動モデル選択」を参照。

## 11. UI品質スコアリング

### 採点の形

`scoreHtml` は**比率**で採点します。積み上げ式ではありません。

```text
score = clamp(round(earned / possible * 100) - penalty, 30, 99)
```

- `award(hit, weight)` — 満たしていれば加点。満たしていなくても **weight は possible に入る**
- `partial(got, weight)` — 段階評価。`got` は `weight` で頭打ち
- `deduct(points)` — 減点。**possible には入らない**（比率を出したあとに引く）

30点は床です。壊れた文書が「何も作らなかった文書」と同じ点に見えないようにするためのもので、
**30点は「最低点」であって「ゼロ」ではありません。**

### 3つのラブリック

| 入力 | 採点関数 |
|---|---|
| ファイル束（React / Vue / Svelte） | `scoreProject` |
| 単一 HTML ページ | `scoreHtml` のフォールバック節 |
| 実行時の測定値（どちらにも加算） | `scoreRuntime` |

出力形式の判定は `detectKind(readProjectFiles(html).keys())` — **トランスポート越しに読みます。**
かつてここが `data-file="..."` 属性を直接読んでいて、フェンス移行後は `paths` が常に空になり、
ファイル構成を問う加点 62点＋ファイル数の 18点、**100点中80点が構造的に到達不能**でした。
9画面の完成したプロジェクトが 30点と表示された原因がこれです。

3形式は同じラブリックで採点されます。以前は React だけが `scoreProject` に入り、
Vue と Svelte は単一ページ用のフォールバック（`<style>` ブロックや文書長を評価する）に落ちていたため、
同等の文書で React 77 / Vue 43 という比較不能な数字が出ていました。

### scoreRuntime — 実際に描画して測った値

静的な検査ではなく、AgentCore Browser で実際に開き、巡回して得た事実だけを扱います。

```text
加点:
  到達率 reach = min(歩けた画面数, 宣言画面数) / 宣言画面数    最大 18
  画面の充填率（平均、0.8 で飽和）                             最大 14

減点:
  空のコンテナ         6/件（上限 12）
  console エラー       8/件（上限 15）
  死んだナビゲーション  5/件（上限 10）
  死んだボタン         4/件（上限 12）
  例外を投げる操作     12/件（上限 24）
  スタブ化された部品   20/件（上限 60）
  小さすぎる入力欄      3/件（上限 10）
  到達できない画面      5/件（上限 10）
  コントラスト不足      4/件（上限 12）
  モバイル横溢         8（4px 超なら一律）
  到達率が半分未満     最大 45（reach=0 で満点の減点）
```

**死んだボタンの件数は、2026-09-13 に巡回の誤検知を直したことで同じ文書でも減ります**（保存済み31件で 45件 → 4件）。
そのためスコアの基準 `SCORE_RUBRIC` を 4 に上げ、バージョンと返答に記録しています（古い基準のスコアは「旧基準」と表示）。

**上限がある減点は、原因が家族で現れるからです。** `.input` クラス1つの誤りが入力欄8件の指摘を生み、
トークンの組み合わせ1つが6件のコントラスト違反を生みます。80点引くべき話ではありません。

**巡回が時間切れ（`truncated`）のときは、到達に関する2つの減点を行いません。**
巡回は20秒で打ち切られ、開けなかった画面は「到達不能」として記録されます。それを減点すると
**文書ではなく探査機の予算を採点する**ことになります。加点のほうは残します —
実際に開けた証拠であり、時間切れでも全画面に到達した文書が点を失う理由はないからです。

### 採点は、出荷する文書を測ったものでなければならない

`scoredFacts` の不変条件は「**捨てた文書の測定値で採点しない**」です。

最終検証から `scoreHtml` までの間に `finalHtml` は最大11回書き換えられます
（stock URL 修復、画像再割当、ルータリンク、runes 正規化、`fixupProject`、拡張子正規化、barrel、
構文修復、埋め込み、トークン除去、スタイル救済）。v156 でそのうち2つを検証前に移して直しましたが、
**残る9つはそのまま**で、同じバグが別経路で戻っていました。

v208 の Vue がその実例です。採点が確定した **9ミリ秒後**に `fixupProject` が
`ReferenceError: props is not defined` を修正してから保存され、
ユーザーが受け取った文書は正常なのに記録は console エラー1件・−8点でした。
今は**文書が実際に変わったときだけ再度巡回**します（ブラウザ1回、モデル呼び出し0回）。

### 監査（defect）の設計原則

指摘は修復パスを1回消費します。したがって:

1. **偽陽性は減点より高くつく。** 疑わしければ黙る。
2. **変更前に 597 文書のコーパスで測る。** 1文書に効く修正は、たいてい過剰適合です。
3. **指摘は「成績」ではなく「依頼」にする。** 「22% しか参照していません」は行動できません。
   「`#6b7280` → `var(--muted)`、対象は `src/components/Card.vue`（14箇所）」は行動できます。
4. **測れない文書は、悪い点をつけるのではなく採点から外す。**
   スタイルシートが読めない文書に 0.43/1 をつけていたのは測定ではありませんでした。
5. **両方向を検証する。** `unreachable-introduced` は `runtimeRegressions(facts, facts)` が
   常に真を返す — つまり**偽になれない**マーカーでした。22件の「壊した」判定のうち13件がこれです。

コーパス実測で正されたもの（2026-08-26）:

| 指摘 | 実測前 | 実測後 | 何が起きていたか |
|---|---|---|---|
| `route-unrendered` | 27件 | 0件 | フォールバック判定が React の綴りしか知らず、`v-else` / `{:else}` / 素の `return X;` を読めなかった。加えて `screenMap` の裸のキーを「未描画」と数えていた |
| `shell-without-nav` | 238件 | 161件 | 58件はシェルに手書きの `<nav>` があった。「画面同士が行き来できない」は事実でなかった |
| `required-prop-missing` | 78件 | 52件 | 31件が `children`。要素の本体で渡すものを属性として探していた |
| `thin-stylesheet` | 99件 | 7件 | 92件が `scoped-styling` と同時に出て、**逆の修復を指示していた** |

`emoji`（27件）と `default-palette`（18件）は実測の結果いずれも本物で、変更していません。

### 単一画面のブリーフについて

`reach` は `declaredScreens > 1` のときだけ問われます。1画面のブリーフが1画面に到達するのは
完成であって幸運ではないためです。一方、ファイル数・部品数の加点は画面数に比例するため、
単一画面のプロジェクトは構造的にやや不利になります。**これは変更しないと決めました** —
コーパス 166 文書のうち該当は2件で、そのために採点を分岐させる価値がありません。

### 12.1 パイプラインエラー

| エラー種別 | リトライ | ステータス |
|-----------|---------|----------|
| Bedrock API エラー | なし | 502 / エラーメッセージ |
| 入力バリデーション失敗 | 不可 | 400 |
| Guardrail ブロック | 不可 | 400 |
| 認証エラー | 不可 | 401 |
| 使用量超過 | 不可 | 403 |
| レート制限 | 待機後可 | 429 |
| Lambda タイムアウト | 不可 | 504 |

### 12.2 ポーリングエラー処理

フロントエンドのポーリングフック（useGenerate, useModify, usePlan）は以下の方式でエラーを処理します：

```typescript
.then(async (res) => {
  if (!res.ok) {
    const err = new Error(`Poll failed: ${res.status}`);
    (err as any).status = res.status;
    throw err;
  }
  return res.json();
})
.catch((err) => {
  const status = (err as any).status;
  if (status >= 400 && status < 500 && status !== 429) {
    // 4xx（429 除く）→ リトライ停止・認証エラー表示
    setError('認証エラーが発生しました。再度ログインしてください。');
    setIsProcessing(false);
    return;
  }
  // それ以外 → バックオフ後リトライ
  pollTimerRef.current = setTimeout(() => pollJob(...), POLL_INTERVAL_MS * 2);
})
```

### 12.3 フォールバック

| コンポーネント | フォールバック |
|--------------|-------------|
| Memory 検索失敗 | 空配列返却、パイプライン続行 |
| KB 検索失敗 | 空配列返却、パイプライン続行 |
| S3 保存失敗 | ログ出力のみ、結果は返却 |
| token-usage.ts 保存失敗 | ログ出力のみ、ジョブは成功として扱う |
| fullHtmlModify パース失敗 | 診断メッセージ付きで例外（入力をそのまま返さない） |
| 設計グラフの失敗・タイムアウト（ログ `Design swarm failed`） | 単一呼び出しの設計フェーズへフォールバック |
| AgentCore Runtime 呼び出し失敗 | worker Lambda（900秒）へフォールバック |
| Preset SSM 取得失敗 | `digital-agency` + 推定 prefix |

> **意図的なフェイルオープン**: `checkUsageLimit` は DynamoDB エラー時に通します。可用性優先の判断ですが、DynamoDB 障害中は使用量上限が効きません。

## 13. 可観測性

### 13.1 構造化ログ

全ログは JSON 形式で出力（`logger.ts`）:

```json
{
  "timestamp": "2026-08-02T10:00:00.000Z",
  "level": "info",
  "message": "Pipeline completed",
  "requestId": "uuid",
  "duration": 35000,
  "score": 88
}
```

ログの出力先は実行系によって分かれます。

| 実行系 | ロググループ |
|--------|-------------|
| API Lambda | `/aws/lambda/makeui-backend` |
| AgentCore Runtime | `/aws/bedrock-agentcore/runtimes/makeuiBackend-XXXXXXXXXX-DEFAULT` |
| worker Lambda（フォールバック時） | `/aws/lambda/makeui-worker` |

どちらの実行系が使われたかは API Lambda 側の `Job dispatched to ...` で判別できます。Runtime のロググループは、実行ロールに `logs:CreateLogGroup` / `CreateLogStream` / `PutLogEvents` がないと作成されません。

### 13.2 トークン追跡

`services/token-ledger.ts` の台帳が、実行ごとに**モデルの申告値**を工程（stage）別に記録します（§3.0.1）。
申告の無い呼び出しは推定せず「欠落（unreported）」として数えます。以前の `TokenTracker` による文字数推定は
設計フェーズを1トークンも計上しておらず、廃止しました。`InvokeModelCommand` を使うファイルは台帳への記録が
テスト（ledger coverage）で必須です。工程別の集計は `backend/scripts/token-stages.mjs`。

### 13.3 計測スクリプト

CloudWatch のログを読むだけでモデルを呼ばない計測スクリプトが `backend/scripts/` にあります
（一覧は `backend/scripts/README.md`）。2026-09-13 の変更（要件の照合・修復判定・巡回）の効き目は
`pipeline-outcomes.mjs` で読みます。
