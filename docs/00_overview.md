# MakeUI - AI UIデザイン生成アプリケーション

## 概要

自然言語から高精度なUIデザインを生成するAIアプリケーションです。出力はいずれも TypeScript の
マルチファイル構成で、そのまま実開発に転用できるフォルダ構造を持ちます。次の3形式から選べます。

- **React** — TypeScript + JSX。context + reducer で状態を持つ
- **Vue** — Vue 3 の単一ファイルコンポーネント（`<script setup lang="ts">`）

単一 HTML 出力は廃止しました（理由は DESIGN.md 3.1.3）。Angular は見送っています。

ジョブ実行の本体は **Amazon Bedrock AgentCore Runtime** 上で動作します。デザイン設計フェーズは **Strands Agents SDK の Graph** で構成し、**どの専門家を走らせるかは依頼内容から動的に決めます**。各エージェントは Agents-as-Tools として Bedrock KnowledgeBase を直接引けます。コード生成フェーズは `InvokeModelWithResponseStream` によるストリーミングで、推論の過程と結果をチャットに逐次表示します。

セキュリティは Cognito（MFA必須・管理者招待制）+ CloudFront（HTTPS配信）+ Bedrock Guardrails（コンテンツフィルタ・PII保護）で確保します。

### なぜ Lambda ではなく AgentCore Runtime か

| | worker Lambda | AgentCore Runtime |
|---|---|---|
| 実行時間上限 | 900秒（固定） | セッション最長8時間 |
| 同時実行の分離 | 関数の同時実行枠を共有 | ジョブごとに専用 microVM |
| マルチエージェント | 900秒制約で載せられない | 設計 Graph + コード生成を同一セッションで実行可能 |

React のマルチ画面プロジェクト生成は設計フェーズだけで 60〜260秒かかるため、Lambda では設計を厚くするほどコード生成が枯渇していました。Runtime への移設でこの制約が外れています。

`dispatchJob()`（`lambda-handler.ts`）は Runtime を第一候補とし、失敗時のみ worker Lambda に落とします。障害時は旧来の 900 秒パスに縮退するだけで、リクエスト自体は失敗しません。

## プランモード（POST /plan）

生成のコストの大半は Step 1 の設計フェーズにあり、そして最も変更したくなるのもそこです。作ってから直すと修正1回ごとにフルビルドの費用がかかるため、**設計フェーズだけを実行して止まるモード**を用意しています。

```text
POST /plan  → Step 0 + Step 1 のみ実行 → { plan: 提案文, spec: 設計仕様 }
                                             ↓ ユーザーが承認
POST /generate { approvedPlan: spec } → Step 1 を丸ごとスキップして Step 2 から
```

`spec` を承認時にそのまま渡すのが要点で、渡さなければ設計フェーズの費用が二重にかかるうえ、レビューした内容と違うものが出来上がりかねません。承認を挟んでも合計時間は通常生成とほぼ変わりません。

## 生成パイプライン（POST /generate）

```text
[プリフェッチ]
  └─ KnowledgeBase: プリセット別デザインシステム文書を検索
     （Memory は設計フェーズが自分で取得する。ここで取っていた分は
       どこからも読まれておらず、毎回の生成が無駄な検索を1回払っていた）

Step -1: どの工程を走らせるか（config/effort.ts）
  モード（下書き / 仕上げ）が、検査する工程を走らせるかどうかだけを決める。
  設計グラフ・ブラウザ検証・修復ループ・視覚批評の4つが対象。
  下書きはそれらを落とすため完成度が下がる — それが選択の中身なので、
  工程をこっそり残して同じ結果にすることはしない。
  既定（仕上げ）はこの設定が無かった頃とまったく同じ値。

  モデルは決めない。以前は4モードのうち3つがモデルを固定し、モデルピッカーを
  無効化していた。1つの決定に2つのコントロールがあり、しかも軸が2本あるものを
  1本のダイヤルに載せていたため順序が成立していなかった — 30日の実測で、
  節約(Haiku)は67%が初回コンパイルに失敗して4コール/85kトークン/中央値440s、
  高速(Sonnet)は25%/2コール/50k/278s。工程は高速の方が多いのに高速の方が速い。
  いまはモードが検査の有無、ピッカーがモデルを決める。旧4名称は意味で読み替える
  （economy・fast → 下書き、standard・thinking → 仕上げ）ので、保存済みのジョブや
  古いタブからの値もそのまま通る。
  環境変数（DESIGN_SWARM_ENABLED など）とは別のゲートで、両方が許可した工程だけが走る。
  「この配備で何ができるか」と「この依頼が何を望むか」は別の問いなので分けてある。

Step -0.5: 計測とタイムアウトの土台
  トークンは AsyncLocalStorage の台帳に、各呼び出しがモデルの申告値を入れる
  （services/token-ledger.ts）。以前は文字数を4で割る推定で、4エージェントの
  設計フェーズは1トークンも計上されていなかった — 下書きが省く工程こそが
  計上されていない工程だったので、モードを変えても使用量が動かなかった。
  申告の無い呼び出しは推定せず「欠落」として数える（実数に推測を混ぜない）。

  Bedrock クライアントは1箇所で生成し、requestTimeout=10分を必ず持つ
  （config/bedrock-client.ts）。以前は4モジュールが個別に生成しどれも無制限で、
  実測で1回の呼び出しが32分間無応答のままジョブが止まったことがある。

Step 0: 構成の決定（workflow-router.ts）
  依頼内容を分類し、どの専門家を走らせるかを決める（安価な1回の呼び出し）
  失敗時は決定的な規則にフォールバック — ルーターが生成を止めることはない

Step 0.5: 要件の抽出（requirements.ts）— 設計フェーズと並行
  依頼文を Haiku 1回で「機械的に確かめられる要件」のリストにする:
    text（画面に出す文言。「フッターに」「〇〇画面に」の場所つき）/ absent（出さない文言）/
    key（キー操作。Ctrl+K なども）/ screen（名前を挙げた画面）/ behaviour（確かめられない）
  text・absent・key・screen は設計フェーズ（専門家と批評役）とビルドのプロンプトに「照合される要件」として添え
  （2026-09-14〜。設計の前に抽出を最大15秒待つ）、完成物で照合し、
  満たしていないものは requirement-unmet として修復ループに入る。
  返答には「自動で確認できる N 件中 M 件を満たしています」と出す。失敗しても生成は止めない。
  詳細は 04_backend.md「要件の照合と、修復の判定」

Step 1: デザイン設計（Strands Graph / strands-design.ts）
  Step 0 が選んだ専門家だけを、この順で固定実行する:
    layout-architect     画面構成・情報設計・保持する状態と変更アクション（常時）
    interaction-designer 全操作要素を列挙し、何がどう変わるかを1行ずつ確定
    style-expert         階層・密度・構図と、描く図版。プリセットが束縛されている
                         ときはトークンを選び直さず、「どの要素が支配的か」「どれだけ
                         密か」を決める（後述）
    content-strategist   実コンテンツ・空状態・検証メッセージ
    design-critic        組み上がった仕様を検査し、**その場で編集する**
                         （スタブ画面・死んだコントロール・戻り経路の欠落・汎用的な
                         コピー・専門家間の矛盾）。`### FIX:`（引用して置換）と
                         `### ADD:`（末尾に追記）の2形式のみ。
                         **引用しなかった部分は失われようがない**ので、守るべき長さが
                         存在しない。以前はセクション全文を書き直させており、実測で
                         4回中3回が「短すぎる」として却下されていた
                         （10,327文字 → 1,019文字など）。
                         パーサは `backend/test/critic-edits.test.mjs` で検証（16件）

  各専門家は**自分のセクションだけ**を書き、コードが機械的に連結する。
  以前は「最後のノードが全体をまとめ直す」構造だったが、4人ぶんをモデルの記憶から
  再現させる工程で欠落が起き、しかも連結の末尾（＝完成した仕様）がビルド側の
  20,000文字の切り詰めで真っ先に捨てられていた（実測 149,283文字中 86.6% 破棄）。
  現在は全量がビルドに届き、切り詰めが効いたときはログに出る。

  各エージェントは Agents-as-Tools として次を呼べる:
    lookup_design_system        プリセット別のコンポーネント／レイアウト実装レシピ
    lookup_interaction_patterns 共通のルーティング・状態遷移・モーダル・ARIA パターン

  AgentCore Memory を読むのはこのフェーズだけ。プリセットが束縛されている
  ときは引かない（レコードが持つ値はすべてプリセットが絶対値として指定する
  ため、繰り返すか矛盾するかにしかならない）。引く場合もプリセット一致・
  類似度 0.45 以上のレコードだけを採用する。

  グラフには10分の実行予算がある。**予算を超えた場合、完了した専門家の成果を
  そのまま組み立てて使う**（単一呼び出しへのフォールバックはしない）。以前は
  SDK が例外を投げ、完了済みのレイアウト・操作・ビジュアル設計を丸ごと捨てて
  最初からやり直していた — 実測のユーザー実行2件で、10分を捨てたうえで
  合計21分を超えていた。ノードごとの出力はストリーム時に控えてある。

  ※ DESIGN_SWARM_ENABLED=1 のとき有効（Runtime のみ）。
     グラフ自体が起動しない場合は従来の単一呼び出し設計フェーズへフォールバック。
     この環境変数が消えると設計グラフは起動せず、`Design swarm failed` も
     出ないまま毎回フォールバックする（update-agent-runtime は全置換）。

Step 2: code-assembler
  入力: 設計仕様 + プリセット仕様 (PRESET_SPECS) + prompt
  出力: outputKind (react / vue) に応じたプロジェクト。
        ファイル構成と言語固有ルールは config/frameworks.ts の登録簿から組み立てる。
        文書形式は行フェンス（@@@makeui:file <path> … @@@makeui:endfile）。
        以前の <script data-file="..."> 形式は、SFC が自身の </script> を
        持つため中身が切られる。実測 113 バイト書き込み → 68 バイト読み出し。
        読み手は両形式を解釈する（既存 React プロジェクトは旧形式のまま）。
  InvokeModelWithResponseStream で逐次出力し、900ms ごとに
  DynamoDB のジョブレコードへ streamTail / streamChars を書き込む
  工程が切り替わるたび streamPhase も即時に書き込む（出力を持たない工程も
  フロントの推論トランスクリプトに現れるようにするため。書き込みは直列化する —
  同一キーへの並行 UpdateItem には順序保証がなく、古いラベルが後着すると
  終わった工程で表示が止まる）
  進捗はチャット欄にのみ表示する（プレビュー面への重ね表示は一度入れたが取り止め）

Step 3: 仕上げ
  scoreHtml で品質スコアを算出
  プリセット指定時は presetConformance() で機械的に準拠を検査し、
  完全準拠でない場合のみ補正パスを1回実行

  さらに auditInteractivity() ほかの監査・ブラウザ検証・要件の照合で不備を集め、
  修復ループ（最大3パス。ファイル単位で書き換える）を回す。候補の判定は:
    ① 決定的修復（fixupProject）を先にかける → ② コンパイル →
    ③ 描画してコントラストを自動修正 → ④ 修復前と同じ集め方で欠陥を測り直す →
    ⑤ アプリを壊したら診断をログに出して候補を S3 に残し、ルーティングのファイル、
       次に変更したファイルを1つずつ戻して救済（どこからも使われなくなった新規ファイルは除く）→
    ⑥ 「画面が出ない・届かない・動かない・例外」を重み3、見た目の指摘を重み1として、
       重み付きの不備が減ったときだけ採用する（2026-09-13 以降。以前は件数で比べていた）
  （プリセット補正パスも「計測上改善した場合のみ」採用する）

Step 3a-2: 構文修復（syntax-repair.ts）— モデルを呼ばない
  1ファイルでも壊れていれば「劣化したプロジェクト」ではなく**プロジェクトが無い**のと
  同じです。バンドラは全モジュールを1つの文書にまとめるので、どこか1文字の誤りが
  空の応答とまったく同じ結果 —「ビルドエラー」と真っ白なペイン — を生みます。
  実測: 8画面のECサイトがこれで出荷されました。

      case 'UPDATE_CART_QTY:

  閉じ引用符の欠落です。リテラルは11行下の次の `'` まで走り、パーサはそこで
  `Unexpected token, expected ":" (54:11)` と報告します — まったく正しい行を指して。
  この報告に対して上流は何もできませんでした（修復プランナが受け取るのは、見えない
  ファイル内の位置を含む console-error 1件だけ）。

  この種類は**決定可能**なので、モデルを呼ばずに直します。JavaScript の文字列リテラルは
  生の改行を含めないため、行末までに閉じない引用符は疑いなく誤りです。ただし
  「どこに閉じ引用符があるべきか」は決定可能ではないので推測はしません:
  閉じ引用符が入り得る数箇所を右から順に試し、**そのつど再パースして、ファイル全体が
  通った最初の候補だけを採用**します（`case 'X:` は行末に足すと `'X:'` でまだ通らず、
  1つ左の `'X':` で通る）。検証できない修復は適用しません。

  直せなかったものは `syntax-error` として**ファイル単位で**報告し、per-file 修復が
  答えられる形にします。エラー位置は原因の行とは限らない旨も指示文に含めます。

Step 3b: ブラウザ実行検証（AgentCore Browser / browser-verify.ts）
  ここまでの検査はすべて「ソースを読む」ものです。実際にレンダリングして測ります。
  アプリを歩きながら測るのが要点で、ナビ項目に加えて**一覧行・カード・画面内のボタン**も
  クリックします（詳細画面はナビからは開かないため）。実測 5.5秒:
    画面ごとの表示密度 fill  コンテンツがビューポートの何割の高さまで届くか
    empty-container         描画されているのに中身が空の枠（200x150 以上）
    console-error           実行時に投げられる JS 例外
    nav-dead-runtime        クリックしても**DOM が何も応答しない**ナビ項目
    action-dead-runtime     クリックしても何も起きない画面内のボタン
    input-small             高さ36px未満 / 文字14px未満の入力欄・セレクト・テキストエリア
                            （チェックボックス・ラジオ・スライダーは対象外。小さくて当然）
    preset-drift            バインドされたデザインシステムからの逸脱（ループ内で修復）
    syntax-error            パースできないソースファイル（ブラウザを待たずに名指しする。
                            1つでもあればバンドルが止まり、他の検査は何も見られない）
    screen-unreachable      どの操作からも到達できない画面（誤検出を避けるため、
                            3画面以上に到達できていて、かつ未到達が1つだけのときのみ）

  **「変わったか」ではなく「応答したか」で判定します。** NAV_SELECTOR は nav の中の
  ボタンをすべて拾うので、メニュー開閉・通知ベル・アカウントメニューは「画面が変わらない」
  ことになり、動いているのに死んだナビとして報告されていました。要素数・描画テキスト長・
  状態属性の3点で応答を見ます。同時に、判定条件が「直前のクリックが画面を変えたか」に
  なっていたのを直しました — 各ナビクリックの間に行クリックが差し込まれるようになった時点で
  この条件は成立しなくなっており、**死んだボタンを1つも検出できない状態**でした（実測）。

  画面内のボタンを押すのは、この製品の主張そのものを測るためです。ナビが動いて
  「追加」「保存」が何もしないモックは、動くアプリではなくアプリの絵です。
  破壊的な操作（削除・ログアウト・リセット）と、効果がページ外にある操作
  （コピー・ダウンロード・印刷）は**押しません** — 前者は以降の計測対象を壊し、
  後者は正しく動いていても「死んでいる」と報告されるためです。
  フォーム送信は capture で preventDefault します。モックにサーバは無く、実際に
  送信するとページがリロードして巡回が最初からやり直しになるだけだからです。
  スクリーンショットは visual-critic（Vision）に渡し、タイポグラフィと密度だけを
  指摘させます（階層・余白・整列は修復が一度も効かなかったため、アクセントと装飾事故は
  修復した後の方が、批評をやり直したときより多く残ると測れたため（2026-09-14）、
  聞くのをやめました）。指摘は、修復用の指示と利用者向けの一文の2つを持ちます。

  **巡回の誤検知（2026-09-13 修正）.** 「押しても動かない」は大半が巡回側の誤りでした —
  先に押したボタンが閉じたモーダルの中のボタンを押す、同じ行を2回押す、既に選択済みの
  切り替えボタンを押す、クラスや入力値だけ変わる応答を見落とす、confirm() で止まる、
  固定の未来日付が入力検証で弾かれる。保存済み31件の再巡回で 45件 → 4件。詳細は
  08_agentcore_strands.md。巡回のログには時間切れ・押した数・タイムゾーンを記録します。
  **自動修正の後の測り直し.** 計測の後に決定的修復が文書を変えたときは、出荷前に測り直します
  （以前は修復パスが受理されないと測り直さず、もう無い色の不足を返答に載せていました）。
  修復パスの採用判定では、絶対値の検査に加えて**修復前後の差分**も見ます
  （`runtimeRegressions`）。絶対値の検査は誤検出を避けるため保守的で、その下を
  実際の劣化がすり抜けるためです — 実測で、修復が2画面を到達不能にし、依頼に無い
  `about` 画面まで追加したうえで採用されていました。「さっきまで開けた画面が開けない」は
  巡回の網羅性についての推測ではなく、変更についての直接の証拠なので、差分は厳密に判定できます。
  **空の枠だけは専用パスで埋めます**（`fill-empty.ts`）。汎用の repair パスは
  「既存のマークアップ・デザインを一切変えるな」と指示されており、「この空の箱に
  実データのチャートを描け」と正面から矛盾します。実測でも repair は無関係な
  preset-drift を直して採用され、**空のガントチャートをそのまま出荷**しました。
  専用パスは逆の権限を持ちます — 1つの名前付き要素の**内側だけ**に実質的な内容を
  書いてよい。要素の外側はバイト単位でそのまま繋ぎ直すので、書く権限が壊す権限に
  なりません。埋めた後に再レンダリングし、**空の枠が実際に減ったときだけ採用**します。

  残りの不備は Step 3 の repair パスに合流します。
  測定結果は `metadata.verification` としてジョブ結果に載ります
  （スクリーンショットは載せません — base64 で約40KB あり、DynamoDB の 400KB 制限に対して
  数値のほうが行動に繋がるためです）。
  **UI には出しません。** 以前はプレビュー右上に「実機検証」チップを出していましたが、
  依頼により削除しました。計測は修復ループが消費するものであって、利用者に読ませる
  ものではありません。確認はログ（`Browser verification completed`）で行います。
  ※ BROWSER_VERIFY_ENABLED=1 のとき有効。ブラウザが使えないときは null を返し、
     この工程が無かったときと完全に同じ挙動に戻ります（生成を止めません）。
```

### 動作の機械検査（interaction-audit.ts）

プロンプトは「すべてのボタンを動作させる」よう要求していますが、要求は保証ではありません。品質スコアも見た目を評価するため、**美しいが何も動かないページ**は満点になり得ます。そこで要求をチェックとして書き直しています。

| 検査 | 内容 |
|------|------|
| screens | 画面が3つ以上あるか |
| router | hashchange を購読しているか |
| route-default | hash が空／未知のとき最初の画面へフォールバックするか |
| nav-wiring | ナビゲーションが実際に配線されているか（画面が3つ以上あるときのみ） |
| dead-controls | ボタン数に対しハンドラが極端に不足していないか |
| form-inert | フォームが submit を処理しているか |
| native-dialog | alert() / confirm() を UI 代わりに使っていないか |
| placeholder | 「Coming Soon」等が残っていないか |
| demo-login | ログイン画面があるとき、デモ認証情報が**画面上に表示**されているか |
| input-sizing | 入力欄が実際に打ち込めるサイズか（font-size 16px 以上、高さ/余白の指定あり） |
| route-unrendered | ScreenId のうち App.tsx に描画分岐が無いものが無いか |
| imagery-missing | 図版（空状態・グラフ・ワードマーク）が描かれているか |
| image-hole | 「画像なし」等の未完成を示す文言が残っていないか |
| photo-slot-unsized | 写真プレースホルダに寸法（aspect-ratio / height）があるか |
| static-chart | グラフが固定値で描かれていないか（`.map()` でデータから描いているか） |

`demo-login` は定数の存在だけでなく「デモアカウント」という**表示**も要求します。コード内にしか
存在しない DEMO_ACCOUNT は、モック自身の認証チェックは通す一方でレビュアーは締め出したままだからです。

`route-unrendered` も実測から足しました。既存の `app-fallback` は `switch` がある場合しか
発火せず、生成されるアプリはほぼ全て `{route.screen === 'x' && <XScreen />}` の連鎖で書きます。
そのため**分岐の無い ScreenId が素通り**し、ルーターはそのルートを解釈できるので、遷移すると
真っ白な画面になります。これが `render() は呼ばれましたが画面が空です` の正体でした。
NAV_ITEMS ではなくユニオンと突き合わせるのは、NAV_ITEMS はメニューであり詳細画面や認証画面を
正当に含まないためです。

`static-chart` は実測から足しました。最初の検証で、`<rect>` 3本を固定座標で描いた `DataChart.tsx` が
出力されています。フォルダもファイルも実 SVG も揃っているので構造的な検査はすべて通りますが、
レビュアーはアプリと無関係な数字を読まされます。データ駆動のグラフは必ず入力を `.map()` するため、
そこを測っています。

`input-sizing` は利用報告から足しました。問い合わせフォームの入力欄が小さすぎるという指摘で、
調べるとプロンプト側に**寸法の指定が一切なく**、唯一の記述が「comfortable 10-12px padding」でした。
既定の 14px 文字ではおよそ 38px の箱にしかならず、モデルはさらにラベル幅まで縮めます。実測でも
保存済み生成物 92 件中 38 件が `font-size: 14px` / `height: 36px` 相当でした。

プロンプトに最小値（input/select は 44px・padding 12px 14px、textarea は 140px、いずれも
font-size 16px 以上、フォーム列 420-560px）を明記した上で、検査でも押さえています。判定は
狭く倒しています — 打ち込む対象（text 系 input と textarea）だけを見て、チェックボックスや
`<select>` は除外し、`var(--token)` は解決してから比較し、解決できない値（`clamp()` 等）は
放置します。最初の版はこの限定が無く、テキスト欄が正しく 16px のページを **12px の言語切替
`<select>`** で誤検出していました。

`screens` と `nav-wiring` はログ実測から直しました。`screens` は `data-screen=` と `class="screen"`
の**両方を別々に数えていました**が、生成される `<section>` は両方を持つため常に2倍になります。
2画面のログインデモが4と測れて最低3を通過しており、この検査が捕まえるべきものそのものを見逃していました。
`nav-wiring` は `data-goto=` という**特定の実装だけ**を要求していたため、`<a href="#/cart">` や
クリックハンドラから `navigate()` を呼ぶ正しい実装が「壊れている」と報告され、修正パスは
（直すものが無いので）何も変えられず必ず棄却されていました。現在は3つの書き方のいずれでも通り、
遷移先の画面が足りないときは `screens` に任せて二重報告しません。

### AI っぽさの機械検査（design-audit.ts）

| 検査 | 内容 |
|------|------|
| emoji | UI 中の絵文字（**0個が必須**） |
| default-palette | indigo/violet の既定色（プリセット未指定時のみ） |
| gradient-text | 見出しのグラデーション文字 |
| glass-nav | ヘッダー/ナビの glassmorphism |
| glow-shadow | 色付きのグロー影 |
| filler-copy | 「革新的」「シームレス」等の空疎なコピー |
| placeholder-naming | 「項目1」「サンプルテキスト」等の仮名称 |

絵文字の判定は範囲を絞っており、✓ ✗ → • — ¥ ℃ ± といった組版記号は誤検出しません（20ケースで検証）。

> **Miscellaneous Symbols (U+2600-U+26FF) の除外は広すぎました。** 組版記号を守るために
> このブロックごと外していましたが、そこには ☕ ⚡ ⛄ ⚽ ☀ も入っています。実際に EC サイトの
> 生成物が `<button>☕ コーヒー器具 EC</button>` をロゴとして出力し、**検査は通過**しました。
> 現在はブロックを対象に含め、製品が実際に組版に使う記号だけを除外します — 評価の ★☆、
> チェックリストの ☐☑☒、警告の ⚠、トランプの ♠♥♦♣。
>
> 保存済み119件で確認したところ、**新たに検出された文書は0件**でした（従来51件、変更後も同じ51件）。
> つまり誤検出を増やさずに取りこぼしだけを塞いでいます。

**どちらの検査も、文書のうち実際に出荷される部分だけを見ます**（`withoutProse()`）。生成物は
`SPECIFICATION.md` と `docs/design-guidelines.md` を `<script type="text/markdown">` として同梱しますが、
これはアプリ**についての文書**でありアプリではありません。両検査はここで逆方向に騙されていました。

- `demo-login`: 仕様書はデモ認証情報を書くことが必須なので、**仕様書の文面だけで検査が通り**、
  画面に何も表示しないログイン画面が「表示済み」と判定される。
- `emoji` / `default-palette` / `filler-copy`: デザインガイドラインは禁止事項リストそのものであり、
  「❌ Emoji as icons」「回避: #6366f1, #8b5cf6」「filler copy（「Supercharge」「Seamlessly」）」を
  含みます。生の文書を測ると、**規則を守っている文書が規則違反として報告されます**。

後者は修正不能な指摘でした。修正パスは「絵文字の無い UI から絵文字を消せ」と言われるので何も変えられず、
（計測が改善しないので）正しく棄却され、次の生成でガイドラインがまた書かれます。実測 14 日間で
**指摘が残ったまま終わった 6 実行のうち 4 件がこれ**でした。

誤検出は無駄なモデル呼び出しに直結するため、判定は保守的に倒しています（例: 「準備中」は日本語では正当なステータス値なので検査対象から除外）。

チャット欄には、モデルが本文より前に書いた計画部分を「推論」として、以降を「応答」として分離表示します。進捗は全ステップで逐次表示され、いま何をしているかは `streamPhase` としてジョブレコードに書かれ、そのままチャットのラベルになります。

### 出力形式: React プロジェクト構成

生成物は**プレビュー用の成果物ではなく、そのまま開発を続けるリポジトリ**です。

```text
SPECIFICATION.md               作った UI の仕様（画面・操作・データ・状態・デザイン・認証）
docs/design-guidelines.md      このアプリが従うデザインルール
src/main.tsx                   エントリ
src/App.tsx                    シェルと画面の切り替え
src/routes.ts                  ScreenId / Route / NAV_ITEMS

src/components/ui/             再利用する部品（Button, Card, Modal …）
src/components/icons/          アイコン（インライン SVG）
src/components/illustrations/  図版・空状態のイラスト（インライン SVG）
src/hooks/                     useNavigation ほかカスタムフック

```

`index.html` `package.json` `tsconfig.json` `vite.config.ts` `.gitignore` `README.md` は
フロントエンド側（`virtualFs.toProjectFiles`）が付けます。毎回同一で、かつ細部を外しやすい
定型をモデルの出力トークンで書かせる理由がないためです。

**画面・再利用部品・アイコン・図版を別ディレクトリに分けたのが変更点です。** 以前は
`src/app/components/` に全部入りで、`src/app/screens/` を作ることを明示的に禁止していました。
プレビューするだけなら差はありませんが、**その後も開発を続ける前提では逆**です — 画面は一度
書いて終わり、Button は全員が触る。寿命が違うものを同じ場所に置くと、どちらの都合でも動かせ
なくなります。

副次的な効果として、相対パスが全部1階層になりました（`src/screens/X.tsx` から
`../components/ui/Button`）。旧構成の `../../imports/icons` は、生成されたプロジェクトで最も
多かったビルド失敗の原因です。

`.jsx` / `.js` の生成と `any` の使用は禁止しています。プレビューはブラウザ内で Sucrase により変換して実行するため、バンドラは不要です。

古い構成のプロジェクトも読み込めます。変更指示のプロンプトは構成を指定せず「**この文書に既にある構成を踏襲せよ**」とだけ言うので、編集で作り替えられることはありません。

### プロジェクト記録（recordProjectRun）

ジョブは完了時にプロジェクトへ次を書きます。**ブラウザの有無に依存しません。**

| 項目 | 内容 |
|------|------|
| `lastHtml` | 一覧のサムネイルと再入場時のプレビュー（350KB超は保存しない） |
| `outputKind` | `react` / `vue`。記録が無い場合はファイル拡張子から判定（`.svelte` → svelte、`.vue` → vue、`.tsx`/`.jsx` → react） |
| `totalTokens` | 累計トークン（`if_not_exists` + 加算で原子的に更新） |
| `requestCount` | 生成・変更の実行回数 |

以前 `lastHtml` はブラウザのエフェクトからしか保存されず、ユーザーが別画面にいる間に終わった
ジョブの結果は保存されませんでした。「たまにプレビューが出ない」の原因はこれです。

### 仕様書（SPECIFICATION.md）

生成時にプロジェクト直下へ Markdown の仕様書を出力します。コードを開かずに何が作られたかを
把握するための文書であり、開発を引き継ぐ人が最初に読む文書です。

構成は「作ったもの / 画面一覧（ID・名前・役割・ルート） / 画面ごとの仕様 / データ / 状態と遷移 /
デザイン / 認証 / 対象外」。**実際に作ったものだけを書く**よう指示しています — 依頼文の言い換えや
作らなかった機能が載ると、仕様書としては嘘になるためです。

変更指示のたびに更新します。画面・操作・データ・状態・デザイン方針・認証のいずれかが変われば
該当箇所を書き換え、変わらなければブロックごと維持する、という規則をモディファイのガードに
入れています。

> 仕様書は `<script type="text/markdown" data-file="SPECIFICATION.md">` として運ばれます。
> 2点の副作用に対処済みです。(1) `splitHtmlToFiles` が index.html に `<script src="SPECIFICATION.md">`
> を書き戻してしまうため、Markdown ブロックは参照に置き換えず削除します。(2) 仕様書には
> デモ認証情報を書く決まりなので、`demo-login` 検査の対象から Markdown ブロックを外しました
> — 外さないと「仕様書に書いてある」ことで、画面に出していないログインが検査を通ってしまいます。

### 画像の扱い

#### ユーザーが添付した参照画像

生成・編集・プラン、いずれの入力欄でも画像を添付できます。添付された画像は
**設計フェーズとコード生成の両方に、実際の画像ブロックとして渡されます**
（`src/utils/image-input.ts` が一箇所で data URI を解いて Bedrock の
`{ type: 'image', source: { type: 'base64', … } }` を組み立てます）。

> **かつての不具合**: 画像が渡っていたのは**主張だけ**でした。プロンプトには
> 「A reference image was provided — extract layout structure, color palette…」と
> 書かれる一方で、Bedrock へのメッセージは**テキストのみ**。モデルは「画像がある」と
> 言われながら見えないので、**それらしいものを捏造**していました。無視されるより悪い
> 状態です（参照に従ったように見える出力が返るため）。設計 Swarm も同じで、受け取って
> いたのは `imageProvided: boolean` だけでした。
>
> 編集の経路はさらに手前で切れていました。`/modify` は `input.image` を**検証してから
> ペイロードに入れずに捨てて**おり、フロントエンドはそもそも送っていませんでした。
> つまり不正な画像は拒否され、正しい画像は無視される、という状態です。

画像は 5MB まで許容される一方、非同期 Lambda invoke の上限は 256KB です。そのため
HTML と同じく **S3 経由で渡します**（`uploadImageIfNeeded` / `resolveJobImage`）。
インラインのままでは AgentCore Runtime が使える間だけ動き、ワーカー Lambda へ
フォールバックした瞬間に消えます — つまり Runtime の調子が悪いときだけ壊れます。

添付画像は送信したメッセージのものなので、送信後にクリアします。ただし**プランモードだけは
保持**します（提案を承認して初めてビルドされるため、そのときにまだ必要です）。

#### 添付の経路（2026-09-14 に揃えたもの）

チャットのクリップは1つで、拡張子で「画像」と「データ・資料」に振り分けます。

| 種類 | 拡張子 | 使われ方 |
|---|---|---|
| 画像 | `.png` `.jpg` `.jpeg` `.gif` `.webp`（1枚5MB、最大8枚） | 1枚なら参照か中身かをモデルが判断。2枚以上なら Haiku 1回で説明を付け、依頼文が「参考に」と明示した1枚だけを参照、残りを中身として目印で配置 |
| データ | `.csv` `.tsv` `.json`（512KBまで） | 先頭12行（JSON は5件）と全件数を「実データ」として設計とビルドに渡す |
| 資料 | `.md` `.markdown` `.txt`、`.pdf`（ブラウザで文字を抽出） | 最大4,000文字を「依頼内容の一部」として渡す |

**生成・編集・プランのどれでも、画像の一覧・画像の説明・データファイルが同じように届きます。** 次の抜けを直しました:

- 編集は1枚目の画像しか送らず、残りはクリアされていた。いまは編集でも説明を付けて目印で配置します。中身の画像は説明文だけで足りるので、**ファイル単位の編集のまま**置けます（全体の書き換えになるのは参照画像があるときだけ）
- プランは `images` を受け取っても読んでいなかった。承認後のビルドにも1枚目しか渡っていなかった
- 画像が1枚のとき、説明欄に書いた内容が送られていなかった。いまは参照画像の指示文と alt に使います
- `/modify` と `/plan` はデータファイルと画像の説明を**検証してからジョブに入れずに捨てていた**（上の「かつての不具合」と同じ形）

共通の手順は `orchestration/supplied-images.ts`（プランと編集）にあり、生成は同じ手順を `graph.ts` に持っています。

#### 添付画像を「参照」ではなく「中身」として表示する

添付には2つの意味があり、区別できるのは**プロンプトの文面だけ**です。

| 指示 | 意味 |
|------|------|
| 「この画像のデザインを踏襲して」 | **参照** — レイアウト・配色・タイポを読み取る |
| 「この商品画像を使って」 | **中身** — その画像自体を画面に出す |

リクエストのどこにも区別は無く、モデルだけが文面と画像の両方を持っています。そこで判断は
モデルに任せ、「中身」と判断した場合に置く**目印**を渡します。

```
モデルが書く : <img src="{{USER_IMAGE}}" alt="…">
サーバが置換 : data:image/png;base64,……
```

**data URI をプロンプトに入れることは絶対にしません。** base64 をモデルに書き写させるのは
トークン単価が高いうえ、**1文字ずれれば画像が黙って壊れます**。目印は13文字で、置換は
文字列連結なので失敗しません。

置換は**両方の補正パスが終わった最後**に行います。補正パスは文書全体を書き直し、入力を
120,000文字で切るため、先に data URI を入れるとモデルに書き写させることになるか、
truncation で切り落とされます。目印なら13文字で両方を通過します。

#### 生成物は DynamoDB ではなく S3 に置く

当初この上限は 150,000文字（約110KBの画像）でした。バージョン履歴とプロジェクトのプレビューが
生成物を DynamoDB の項目に**そのまま保存**しており、項目上限が 400KB だったためです。
つまり**「写真の大きさ」が「その実行が履歴に残るかどうか」を決めていました**。

両方とも S3 に移し、レコードには鍵だけを持たせました。

| | 保存先 | レコード |
|---|---|---|
| バージョン履歴 | `versions/{userId}/{versionId}.html` | `htmlS3Key` |
| プロジェクトのプレビュー | `projects/{userId}/{projectId}.html` | `lastHtmlS3Key` |

`jobs/` プレフィックスとは**別にしています**。あちらは7日で失効する中継用で、履歴に同じ
寿命を与えると黙って消えます。

既存レコードは本文をインラインで持っているため、読み出しは**インラインを先に見て、無ければ
S3 から復元**します。インライン読みを外すと既存の履歴が全件空になります。

プロジェクト一覧だけは事情が違い、サムネイル用に `lastHtml` のインラインコピーを
（350KB まで）残しています。一覧のたびにプロジェクト数ぶん S3 を読むのは割に合わず、
大きすぎる生成物はサムネイルが出ないだけで、**プレビュー自体は S3 から開きます**。

上限は 150,000 → **2,000,000文字（約1.5MBの画像）**になりました。根拠も保存ではなく
**編集経路**に変わっています。`POST /modify` は本文をリクエストに載せるため、
API Gateway → Lambda の 6MB 制限が効きます。**送り返せない生成物は編集できない生成物**なので、
`/modify` の受け入れ上限も 500,000 → 3,000,000文字に引き上げました。

#### 生成物の中の図版

**Claude は画像を生成できません**（画像の入力は可、出力はテキストのみ）。Bedrock の
text-to-image は Nova Canvas のみで、東京・バージニアいずれも `LEGACY` かつ本アカウントでは
アクセス拒否、Stability の ACTIVE モデルはすべて画像編集系（画像入力が必須）です。つまり
**このシステムにラスタ画像の生成手段はありません**。

そこで図版は **モデルが書くインライン SVG** で賄います。UI のモックに限れば、これは写真の
代替というより上位互換です:

- パレットのトークンをそのまま使うので、色が必ず合う
- 数百バイトで済む（図版まで data URI にすると生成物が肥大する）
- 解像度非依存で、書き出したプロジェクト内で編集できる

契約として `src/components/illustrations/` を必須にし、空状態の線画、実データから描くグラフ、
プロダクトのワードマークを指定しています。

#### ただし写真だけは描かず、プレースホルダにします

以前は写真の入る枠にも「パレット由来の幾何学的な構成（商品なら抽象的な静物）」を描かせ、
一覧の要素ごとに別々のものを割り当てていました。**EC サイトではこれが裏目に出ます。**
発明された図形の集まりは商品でもなければ正直な空欄でもなく、レビュアーは**それをデザインだと
受け取ります**。

写真に正直な代替物はありません。そこで写真枠は「ここに写真が入る」と示す**意図的な
プレースホルダ**として描きます。

- 実際のアスペクト比の箱（一覧タイルは 1:1、カバー/ヒーローは 4:3 か 16:9）を
  `aspect-ratio` で確保 — **潰れず、伸びない**
- 中立色の面（ページ背景から1段。`#ccc` のような素の灰色やグラデーションは不可）
- 中央に小さな写真アイコン（24〜32px、他のアイコンと同じストローク）と、名称があれば
  キャプションサイズで
- グリッド内は**全タイル同じ**扱い。要素ごとに変えるのが「装飾に見える」原因でした
- `alt` は「その写真が写すはずのもの」を書く（`alt="${商品名}の写真"`）。実写に
  差し替えた時点でマークアップが正しいままになります

アバターだけは例外で、頭文字を色付きの円に置くのは発明ではなく実在の慣習なので従来どおりです。

**検査もこの方針に合わせました。** `image-hole` は従来「プレースホルダらしきものすべて」を
不備として報告していましたが、それは今の方針と正面から衝突します。現在は「画像なし」のような
**未完成を示す文言**だけを対象とし、代わりに `photo-slot-unsized`（写真枠に寸法が無く高さ0に
潰れる）を測ります。**寸法があるかどうかは機械的に判定でき、装飾かどうかは判定できません。**

保存済み生成物119件で確認したところ、この変更で `image-hole` は 5件 → 0件 になりました
（5件はすべて、意図どおりのプレースホルダが誤って不備と報告されていたものです）。

実写が要るユースケースでは、`README.md` が `src/assets/` を作って差し替える手順を案内します。

## 修正パイプライン（POST /modify）

```text
Step 0: 指示の分類（workflow-router.ts）と要件の抽出（requirements.ts・並行）
  visual / content      → 設計パスなし。そのまま編集へ
  structural / behaviour → 設計パスあり（下記）

Step 1: 変更の設計（structural / behaviour のみ）
  生成側と同じ interaction-designer が「ビルド契約」を作る:
  追加/変更される画面、全操作要素と状態書き込み、逆方向の経路、実コンテンツ
  失敗しても編集は続行する（契約が無いと弱くなるだけで、不可能にはならない）

Step 2: 編集
  プロジェクト（参照画像なし）→ ファイル単位の編集（projectFileModify）。画面に置く画像は説明文と目印で渡るので、この経路のまま置ける
    書き換えるファイルを決め（指示が引用した文言を含むファイルを先に探して渡す）、
    1ファイル1呼び出しで書き換える
  それ以外・ファイル単位が降りたとき → fullHtmlModify（全文書き換え、出力上限 64,000 トークン）
    ※ React プロジェクトには REACT_MODIFY_GUARD を前置し、構成・型の維持を強制する
    ※ 変換に失敗した場合は診断メッセージ付きで例外を投げる
  どちらも最後に 拡張子の正規化 → index 補完 → 構文修復 → 決定的修復（fixupProject）

Step 3: 品質検査
  編集の前後で auditAiTells / import の不整合（import-missing・export-missing）/
  presetConformance、構造・振る舞いの編集ではブラウザ検証を取り、
  その編集が持ち込んだ差分と、要件の照合で漏れた指示（場所の誤りを含む）を1回修正する。
  ビルドが通らなくなった修正は採用しない

Step 4: 返答
  依頼の各項目と「自動で確認できる N 件は、変更後のソースで確認しました」。
  確認できなかった項目は理由とともに列挙する
```

プレビューの「修復する」ボタンが送る依頼には、ソースの静的検査で見つかった import の不整合を添えます
（React #130 は原因の import を名指ししないため）。

## Strands Agents SDK の利用状況

TypeScript 版 SDK（調査時 v1.11.2。2026-09-13 時点の解決版は 1.16）が提供するのは `Agent` / `Swarm` / `Graph` / `tool` です。**`Workflow` と `A2A` は存在しません**（Python 版にのみ存在）。本システムでは Python を使わない方針のため、この2パターンは採用していません。

| パターン | 状態 | 箇所 |
|---------|------|------|
| **Graph** | 稼働中 | デザイン設計フェーズ（layout-architect → interaction-designer → style-expert → content-strategist）/ `strands-design.ts` |
| **Agents-as-Tools** | 稼働中 | 設計エージェントからの KnowledgeBase 検索（`lookup_design_system` / `lookup_interaction_patterns`） |
| **動的構成** | 稼働中 | 依頼内容から Graph のノードと辺を組み立てる（`workflow-router.ts`）。編集側は指示を分類し、構造変更のときだけ設計パスを挟む |
| Swarm | 不採用 | 実行順がモデル任せになり、同じ入力で仕様が 46,244 文字 / 1,718 文字と揺れたため Graph に置換 |
| Workflow / A2A | 不採用 | TypeScript SDK に非搭載 |

> **到達不能だったモジュールは削除済みです。** 設計フェーズが `strands-design.ts` の Graph に
> 置き換わった時点で、旧実装の9ファイル（`design-analyst` / `layout-architect` / `style-expert` /
> `component-designer` / `code-assembler` / `prompt-enricher` / `accessibility-reviewer` /
> `quality-reviewer` / `refinement-agent`）と `orchestration/review-swarm.ts`、
> `tools/code-interpreter-tool.ts` は誰からも呼ばれなくなっていました。
> `src/agents/` はその後空になりました。スクリーンショットからの逆生成が専用経路をやめ、
> **画像を添えた通常の生成**になったためです（本線の設計フェーズは元から添付画像を
> デザイン参照として読みます）。**バックエンドはエントリポイントから 100% 到達可能**です
> — 実測 54/54 モジュール。

### 実装上の注意点（実機検証で判明）

- `Swarm` のノードには**一意な `id` が必須**。`name` だけでは "duplicate agent id" で失敗する
- Swarm のハンドオフは structured output 経由で行われるため、**各エージェントの成果物は `content` ではなく `structuredOutput.message` に入る**。`content` には「これから設計して次に渡します」程度の前置きしか入らない
- 同じ理由でハンドオフ自体がトークンを消費する。`maxTokens: 8000` では `Model reached maximum token limit` で落ちるため **32,000 を設定**している

### 未適用の AgentCore 機能に対する評価

「使えるから使う」ではなく、現アーキテクチャで**実際に改善になるか**で判断しています。

> 「見送り」と判断したものは**リソースも消しています**。判断だけ記録して READY のまま残すと、権限・SSM パラメータ・呼び出しコードの一式が「使われているように見える」状態で残り、棚卸しのたびに読み直す羽目になります。実際 Code Interpreter は `InvokeCodeInterpreter` 権限も SSM パラメータも呼び出しコードも揃っていながら、**呼び出し元が到達不能で一度も実行されていませんでした**。

| サービス | 判断 | 理由 |
|---------|------|------|
| **Browser** | **適用済み（2026-08-07）** | 静的解析では届かない欠陥が実測で2件見つかったため実装しました。①スコア92・検出欠陥0のページで、ダッシュボードのコンテンツがビューポートの33%の高さで途切れていた ②「ガントチャート画面を追加」した編集が成功（`changed:true`・欠陥0）を報告しながら、チャート本体が空の箱だった。どちらも正規表現では表現できず、レンダリングすれば一目です。<br>**見送っていた理由（CDP を SigV4 署名した WebSocket で駆動する実装量）は、実際にやると小さいと分かりました**: Node 22 組み込みの `WebSocket` と、既に依存にある `@smithy/signature-v4` の presign で足り、**新規パッケージはゼロ**。文書は `Page.setDocumentContent` で流し込むので、生成物を公開URLに出す必要もありません |
| Code Interpreter | **削除済み** | Python サンドボックスであり、生成物は HTML/TS です。書かれていた用途は「グリッド幅の割り算1回」と「HTML 構文チェック」で、前者はサンドボックスを起動して往復する理由がなく、後者は `interaction-audit` / `design-audit` の静的検査が対象特化で担っています。呼び出し元 2 モジュールがどこからも import されておらず、**デプロイ後一度も実行されていませんでした** |
| Policy (Cedar) | **削除済み** | ツールアクセス制御が目的ですが、エージェントが持つツールは KnowledgeBase 検索2種のみで、いずれも読み取り専用です。守るべき境界が存在しません |
| Gateway | 見送り | 自前のツールを MCP として外部公開する機能ですが、現時点で消費者がいません。Gateway 本体は一度も作られていないのに `makeui-gateway-role` だけが存在していたため、ロールと SSM パラメータを削除しました |

Memory の名前空間はメモリリソースが宣言するテンプレート `/strategies/{memoryStrategyId}/actors/{actorId}/` に従う必要があります。これを外れた名前空間へ書いたレコードは検索から見えません。ストラテジ ID は `/makeui/agentcore/memory-strategy-id` に格納しています。

## セキュリティ構成

| 層 | 実装 |
|---|---|
| 認証 | **Cognito** (MFA必須・管理者招待制・12文字以上パスワード) |
| トークン更新 | 15分間隔 + フォーカス復帰時に ID トークンを再取得（有効期限60分） |
| フロントエンド配信 | **CloudFront** (HTTPS + OAC + S3) |
| コンテンツフィルタ | **Bedrock Guardrails** (ApplyGuardrail) + 日本語パターンによる補完（後述） |
| レート制限 | DynamoDB Token Bucket (モデル別コスト重み付け) |
| トークン使用量制限 | DynamoDB でユーザーごと月次上限管理 |
| 管理者機能 | Cognito Groups (`admin`) で管理パネルアクセス制御。自アカウント削除は不可 |
| プレビュー隔離 | iframe `sandbox="allow-scripts"` + previewGuard.ts でフレーム外への遷移を制御。ハッシュはガードが自分で実行し、防げない `location.href` 代入は Preview.tsx のウォッチドッグが書き戻す |
| ジョブ所有権 | `GET /jobs/:id` は `job.userId !== auth.userId` で 403 |
| パス検証 | `/publish` の page.id と KB アップロード名をサニタイズ |
