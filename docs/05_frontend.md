## 認証フロー (Cognito + MFA)

MFA は**必須**です。無効化する導線はありません。

1. メールアドレスとパスワードを入力
2. 初回ログイン時
   - `NEW_PASSWORD_REQUIRED` チャレンジ → 新しいパスワード（12文字以上）を設定
   - MFA (TOTP) セットアップ画面へ遷移し、QR コードを認証アプリでスキャンして6桁コードを入力
3. 通常ログイン時はパスワード認証後に TOTP コードを入力
4. 認証成功後、Cognito ID Token を取得し `Authorization: Bearer <ID Token>` を付与

### トークン更新

ID トークンの有効期限は60分、リフレッシュトークンは7日です。長時間の生成中に期限切れでポーリングが 401 になる問題を避けるため、`AuthProvider` が **15分間隔**とウィンドウのフォーカス復帰時にトークンを再取得します。`useGenerate` / `useModify` はポーリングのたびに `tokenRef.current` から最新トークンを読みます。

## 生成フロー（useGenerate）

SSE ではなく **非同期ジョブ + ポーリング** 方式です。

```text
1. POST /generate → 202 Accepted { jobId }
2. GET /jobs/:jobId を 2秒間隔でポーリング（最大 900 回 = 30分。超えると待機をやめるが、ジョブは残り再アタッチできる）
3. streamPhase / streamTail / streamChars / streamTokens → phaseTranscript.appendPhase() で
   工程ごとの記録に畳み込み、ReasoningTranscript に表示
4. status === 'completed' で result.html を表示
```

ポーリング上限が16分なのは、Runtime 側のジョブが10分を超えることがあるためです。以前は300回（10分）で、成功直前のジョブをクライアントが見捨てていました。

4xx（429 を除く）を受信した場合はリトライを停止して認証エラーを表示します。

### 実行中の表示（ActivityCard / ReasoningTranscript）

実行中のジョブは、Claude Code と同じ**時系列のトランスクリプト**として表示します。

```text
┌─ ActivityCard ────────────────────────────────┐
│ ◐ UIを生成しています                   2分14秒 │
├───────────────────────────────────────────────┤
│ ● 画面構成を設計中        4,180 tok    27秒 ▸ │ ← 完了。折りたたみ
│ ● 操作の挙動を設計中     11,902 tok    46秒 ▸ │
│ ◐ コードを生成中         38,455 tok    49秒 ▾ │ ← 実行中。自動で開く
│   │ 会議室予約システムを作ります。一覧を…      │   ← その工程の散文
│   │ ┌─────────────────────────────────┐ ▲    │
│   │ │ <section class="screen" id=…     │ █    │   ← 出力（高さ190px・追従）
│   │ └─────────────────────────────────┘ ▼    │
└───────────────────────────────────────────────┘
```

**なぜ固定ステップ一覧をやめたのか**: 以前は「工程のドット一覧」と「共有の推論ボックス」の2段構成でした。いま何段階目かは分かりますが、**その工程が何を決めたのかは、次の工程が始まった瞬間に消えていました**。工程ごとに推論を持たせれば、終わった工程を開き直して読めます。所要時間もその場に残ります。

**サーバは現在の工程しか送ってこない**（全文はポーリングに載せられないため、末尾6,000文字＋ラベルのみ）ので、履歴はクライアントが作ります。`appendPhase()` はラベルが変わったら前のエントリを閉じて新しいエントリを開く、それだけの畳み込みです。

**末尾しか届かないことによる罠**: 工程の出力が数万文字になると、散文と本文の境界である `<!DOCTYPE html>` が転送ウィンドウの外へ流れ出します。境界が見つからないからと素朴に「全部が散文」と扱うと、**生の HTML が推論として表示されます**（実装中に実際に起きました）。対策は2つで、境界を一度でも見たらラッチする、そして総文字数が転送幅を超えていたら散文はもう流れ去っていると判断する、です。

**なぜ文字数ではなくトークン数なのか**: 文字数は「その工程がどれだけ書いたか」であって、**どれだけ掛かったかではありません**。大きな文書を読んで一行だけ返す工程は、高価なのに「ほぼ0文字」に見えます。実際の消費はトークン台帳（`token-ledger.ts`）が持っているので、それを表示します。

台帳は**実行単位**で、どの工程のときにどのモデル呼び出しが起きたかは知りません。そこでサーバは各ポーリングに**実行の累計**（`streamTokens`）を載せ、クライアントが工程の境界で差分を取ります。

差分の難所は算術ではなく**いつ数字が届くか**です:

- 工程が開いた時点ではまだどの呼び出しも報告していないことがある → 基準値は「最初に数字が届いたポーリング」で確定します。工程が開いた瞬間に取ると、**前の工程の消費をこの工程に付け替えてしまいます**
- ストリーミング呼び出しは**完了時に**使用量を報告するので、工程の前半は差分0のままです
- 差分0は `0 tok` ではなく**非表示**にします。0と表示すると「この工程は無料だった」と主張することになり、まだ報告が来ていないだけの状態と区別がつきません。ついでに、`undefined → 0` の変化で毎回 React が再描画するのも防げます
- 累計が巻き戻った場合（再実行が古い値を書いた等）も非表示にします。`-800 tok` を出さないためです

**いまの限界（設計フェーズは1つの塊です）**: この方式が効くのは、台帳が呼び出し完了のたびに報告を受ける工程です — コード生成と修復パスがそれにあたります。**設計グラフは効きません**。SDK がこのグラフの使用量を「グラフ全体が返った時」にしか報告しないため、5人の専門家それぞれの工程は数字を持たず、設計費用の全額がその瞬間に走っていた工程に乗ります。

実測（同一依頼を2回）:

```text
画面構成を設計中      0
コンテンツを作成中    0
設計をレビュー中      88,602   ← 設計費用の全額がここに乗る（1回目）
React生成             95,887   ← 2回目はコード工程に乗った
```

**2つの経路を試して、どちらも測って駄目でした**:
- `AfterNodeCallEvent.result` — そんなフィールドは存在しません（`orchestrator` / `state` / `nodeId` / `invocationState` / `error` のみ）
- `AfterNodeCallEvent.state.usage` — 型定義には "aggregated token usage across all node results" とありますが、実測では各ノード完了時점で0のままで、返り値にしか入りませんでした

きちんと直すには SDK からノード単位の使用量を得るか、専門家を個別呼び出しにするかのどちらかが要ります。**進捗ラベルのために払うコストとしては見合わない**と判断し、いまは粗いままにしてあります。

**`chars` は残しています。** 表示には使いませんが、`splitStream()` が「境界の見えない末尾は本文か」を判断するのに使っており、これはトークン数では答えられません（問いが文字通り「何文字が転送ウィンドウの外へ流れたか」であるため）。

**スクロール追従**: 出力ペインは自動で末尾に追従しますが、ユーザーが上へスクロールしたら止まります（末尾24px以内で判定）。スレッド自体の自動スクロールは `streamPhase` の変化時のみで、トークンごとには行いません。

### モード（下書き / 仕上げ / プラン）

入力欄のプルダウンで切り替えます（モデル・デザイン・形式と同じ `Dropdown`）。

パイプラインには元から高価な工程が4つあります — 4エージェントの設計グラフ、ブラウザ実行検証、その後の修復ループ、視覚批評。これまでは**すべての生成がその全部を払っていました**。既定としては正しく、唯一の選択肢としては誤りです。最初のラフに設計グラフは要りません。

| モード | 設計グラフ | ブラウザ検証 | 修復 | 視覚批評 | モデル |
|--------|:---:|:---:|:---:|:---:|---|
| 下書き | — | — | 0回 | — | 選べる |
| 仕上げ | ✅ | ✅ | 3回 | ✅ | 選べる |
| プラン | 設計フェーズだけ実行して停止（`POST /plan`） | | | | |

**下書きは完成度が落ちます。** それがこのモードを選ぶときの取引なので、工程をこっそり残して「実は同じでした」にはしていません。メニューの説明文にもそう書いてあります。

KB検索と画像枚数は**両モードで同じ**です。それらは検査ではなく入力なので、この軸には属しません。以前は `fast` にあって `economy` に無く、「安い」が「工程が少ない」と「文脈が少ない」の2つを同時に意味していました。

#### モードはモデルを決めません

以前は4モードのうち3つがモデルを固定し、モデルのプルダウンをロックしていました。**1つの決定に2つのコントロールがあり、片方が黙って勝つ**構造です。

そして軸が2本あるものを1本のダイヤルに載せていたため、順序が成立していませんでした。30日の実測：

| | 初回コンパイル失敗 | コール数 | 出力トークン | 中央値 |
|---|---:|---:|---:|---:|
| 節約 (Haiku) | 8/12 = 67% | 4 | 84,829 | 440s |
| 高速 (Sonnet) | 2/8 = 25% | 2 | 50,155 | 278s |

**工程表の上では高速の方が多く払っているのに、実測では高速の方が速い。** 弱いモデルがビルドを2.7倍壊し、壊れるたびに緊急修復パスを買っていたためです。両端が入れ替わりうるものはダイヤルではありません。

いまはモードが検査の有無だけを決め、モデルはピッカーが決めます。旧4モードが表現できた組み合わせはすべて再現でき、加えて**「仕上げ × 安いモデル」**が選べるようになりました — 検査つきで最も安い組み合わせで、これまで到達できず、したがって計測もされていませんでした。

**管理者の許可集合は最後に必ずクランプ**するので、許可されていないモデルは渡りません。

> 旧4名称（`economy` / `fast` / `standard` / `thinking`）は意味で読み替えます。保存済みのジョブ、開いたままのタブ、8月に書かれたバージョン行がその名前を送ってくるので、拒否すると「もう無いメニュー項目のせいでビルドが失敗する」ことになります。`backend/test/mode-model.test.mjs` が、モデル表が**両側から消えていること**と、両側のモード一覧が一致することを読みます。

**既定は動かしていません。** 仕上げの値は、この設定が存在しなかった頃のパイプラインとまったく同じです（設計グラフあり・検証あり・修復3回）。既定を動かすと追加ではなく作り直しになります。

`chatMode`（build/plan）と `effort` は内部的には別の状態です。1つにまとめると、プラン承認後のビルドが常に既定に戻り、選んでいた「下書き」が黙って捨てられます。

提案には「このプランで作成」ボタンが付き、押すと `approvedPlan` 付きで生成が始まります。**設計仕様をそのまま渡すので、承認後のビルドは設計フェーズを丸ごと飛ばします**（`Building from an approved plan` → design-analyst 1ms）。

### スコアは「検証あり」と「静的のみ」で比べられません

これはモード追加で持ち込んだ落とし穴で、実装中に実測して気づいたものです。

ブラウザ計測が無いと、**実行時の減点が1つも入りません** — 死んだ操作・空の枠・到達不能な画面・コントラスト・モバイル溢れ。同じ依頼・同じモデル（Haiku）で **下書き 89 / 仕上げ 73**。下書きのほうが良かったのではなく、**調べられていない**だけです。

2つを同じスレッドに並べると事実と逆のことを伝えるので、`metadata.scoreVerified` を返し、検証していないスコアには「静的のみ」と添えます。

### モードのコスト（実測・同一依頼・Haiku・逐次実行）

| | 入力 | 出力 | 合計 | 所要 |
|---|---:|---:|---:|---:|
| 下書き | 20,156 | 43,765 | **63,921** | 4分09秒 |
| 仕上げ | 80,781 | 51,627 | **132,408** | 4分40秒 |

仕上げは下書きの **2.1倍**。差の大半は**入力**（4倍）で、これが設計グラフと修復の入力です。

この数字が出せるようになったのは計測を直したからです。旧計測では同じ比較が「下書き 65,943 / 仕上げ 59,810」— **下書きのほうが高く**出ていました。文字数を4で割る推定だったため、測っていたのは HTML の大きさで、仕事の量ではありませんでした。**設計フェーズは1トークンも計上されていませんでした**（詳細は DESIGN.md §3.0.1）。

提案には「このプランで作成」ボタンが付き、押すと構築モードに切り替わって `approvedPlan` 付きで生成が始まります。**設計仕様をそのまま渡すので、承認後のビルドは設計フェーズを丸ごと飛ばします**（`Building from an approved plan` → design-analyst 1ms）。提案が気に入らなければ、そのまま入力欄に修正点を書けば作り直せます。

プランも `activeJob` に記録されるため、離脱して戻れば再アタッチします。設計フェーズは数分かかるので、生成と同じ理由で捨てるには惜しい処理です。

### チャットの表示様式

Figma Make に倣い、話者で表示を変えています。

| 役割 | 表示 |
|------|------|
| ユーザー | 右寄せの淡い青の吹き出し（角丸14px、右下のみ4px） |
| アシスタント | 左寄せの地の文＋グラデーションのアバター。囲みなし |

長い生成結果を狭い色付きボックスに閉じ込めないための非対称です。スコア・トークン数・時刻はメタ行にまとめ、時刻はホバー時のみ表示します。

**各返信には「何が作ったか」を出します** — `Haiku · Warm` の形式で、モデルとデザインプリセット。

`auto` を選んだときに「自動」と書くのは問いへの答えになっていないため、**解決後の実 tier** を
バックエンドから返しています（生成 / 修正 / プランの3経路すべて `metadata.modelTier` / `preset`）。

プリセットは選択 UI の**短縮名**（`Preset.chip`）を使い、正式名称は tooltip に入れます。
380px のチャット欄で「デジタル庁デザインシステム」を出すとメタ行が3行（55px）になり、
注釈のほうが本文より高くなるためです。短縮名にして 26px（1行）、全行で溢れゼロ。

過去の返信にはチップを出しません。当時のモデルは記録されておらず、
いまのコンポーザーの値で埋めるのは記録ではなく推測です。

保存側にも手を入れています。`useChatHistory` は保存時にフィールドを**ホワイトリストで
削ぎ落とす**ため（`html` を保存しないための正しい仕組み）、追加したフィールドは
明示的に足さないと再読込で消えます。追加漏れは再読込まで表面化しません。

**実機検証チップは削除しました。** 計測はジョブ記録とログに残り、修復ループが消費します。

**返答の後半（計測した事実）.** 生成の返答は、モデルの前置きの後に次を出します
（`backend/src/orchestration/reply-text.ts` が組み立て、`formatReply.ts` が整形）:

- 到達できた画面数とコンソールエラー、作った画面の名前（画面ごとの CSS ファイルは画面として数えない）

### 書体が本番で適用されていなかった（修正済み）

`index.css` は Google Fonts を `@import` していますが、CloudFront の CSP は

### 効きようのない宣言の削除

同じセレクタが最大5回再定義されており、`.app__chat-pane` は `background` を4回宣言していました。
効くのは最後の1つだけで、**先頭を編集しても何も起きません**。これが実際の保守コストでした。

```
BEFORE  .app__chat-pane
  L 259: display, flex-direction, background, border-right, overflow, max-height…
  L1872: background, border-right, max-height
  L2655: border-right, border-bottom, max-height
  L6620: background          ← 効いていない
  L7721: background, border-right   ← これだけが効く
```

適用した規則はひとつだけです。

> 同一の at-rule 文脈で**セレクタ文字列が完全一致**する2つのブロックが、どちらも同じプロパティ
> P を宣言しているなら、先のほうの P は決して勝てない（詳細度も重要度も同じで、後勝ち）。
> **間に何があろうと**削除して計算値は変わらない。

意図的にやっていないこと:

| やらないこと | 理由 |
|-------------|------|
| ブロックの併合 | 宣言を後方へ動かすと、間にある他の規則との勝敗が変わる |
| `!important` が絡むもの | 先が important・後が通常なら先が勝つので、上の論法が反転する |
| ショートハンドと個別指定の解釈 | `background` と `background-color` は別プロパティとして扱う。残しすぎる側が安全 |

結果: 死んだ宣言 551件、空になったブロック 92件、`@keyframes chat-typing`（二重定義のため
前者が完全に無効）1件を削除。**7,748 → 6,959行**、ビルド後 116,963 → 102,446 bytes。

### プロジェクト一覧のカード

カードには出力形式（React / Vue / Svelte）と、そのプロジェクトの累計トークン数・実行回数を出します。

形式は `outputKind` として**ジョブが記録します**。この項目が無い過去のプロジェクトについては、
保存済みの文書が持つファイルの拡張子から判定します（`.svelte` → Svelte、`.vue` → Vue、

再入場や編集の際に依頼文が手元に無いことがあるためです。

形式の記録が無く、拡張子からも判定できない古い文書（50件中34件は HTML でした）は React として

**まとめて操作.** 一覧を選択モードにすると、カードを複数選んで**まとめてアーカイブ**、アーカイブ済みの一覧では
**まとめて削除**ができます（`useProjects` の `archiveProjects` / `deleteProjects`。1件ずつの API を同時4本までで呼ぶ）。

### なぜプレビューが「たまに」出なかったのか

`lastHtml` は**ブラウザだけが書いていました**。生成完了時に走るエフェクトから保存していたので、
ユーザーが別の画面にいる間にジョブが終わると誰も保存せず、プロジェクトは中身が無いまま残ります。
再入場時のバージョン履歴からの復旧はありましたが、それは取りこぼしの後追いです。

いまはジョブ自身が `recordProjectRun()` で書きます。ジョブは文書も projectId も持っているので、
**誰かが見ているかどうかと結果が無関係になりました**。使用量カウンタも同じ関数で更新します —
1回の実行 = 1リクエスト = N トークンという同じ事象であり、別々に数えると必ず食い違うためです。

実測（ブラウザを一切介さず API のみで modify を実行）:

```
BEFORE: outputKind=null   totalTokens=null    requestCount=null   lastHtml=87,455
AFTER : outputKind=react  totalTokens=88,044  requestCount=1      lastHtml=87,674
```

#### 一覧のコピーではなく「いま描けるもの」で判定する

復旧の発火条件は `project.lastHtml` — **一覧から持ち込まれたコピー**でした。これは一覧を
最後に取得した時点のスナップショットなので、生成してから戻ると**実行前**の文書を持っている
ことがあり、逆にキャンバスが空なのに値を持っていることもあります。どちらにせよ、
誰も訊いていない問いに答えています。**重要なのは、このコンポーネントがいま描けるものを
持っているかどうか**です。

現在は `loadedHtml` が空であることを条件にしています（生成中は除外 — 実行中の生成は
まだ文書が無くて当然で、そこで再取得すると実行と競合します）。projectId ごとに1回だけ
走るので、本当に文書が無いプロジェクトが毎レンダー要求を出すことはありません。

サーバ側も直しました。`GET /projects/:id/preview` は**バージョン履歴だけ**を見ていましたが、
文書のコピーは2つあり、それぞれ別の理由で欠けます。

| コピー | 欠ける条件 |
|--------|-----------|
| プロジェクト自身（`lastHtml` / `lastHtmlS3Key`） | 生成後の保存で失敗した実行 |
| バージョン履歴 | 監査を通過しなかった出力（そもそも書かれない） |

プロジェクト側を先に、次に履歴を見ます。**全部のコピーが本当に無いときだけ空になります。**

#### それでも「たまに」出なかった残り — 1つの属性を3者が書いていた

上記は「文書が無い」側の話で、**文書はあるのに描かれない**という別系統が残っていました。

`srcdoc` を書いていたのは3者です — React の `srcDoc` prop、命令的な `setAttribute`、
そして `onLoad` ハンドラの直接代入。さらに「いま来たロードは自分が起こしたものか」を
**真偽値1つ**で管理していました。

プロジェクトを開くと書き込みが3回連続します:

```
1. 生の未コンパイル React ソース（compiling がまだ false）
2. コンパイル中に保持する空文書
3. コンパイル済みの実文書
```

3回の書き込みに対してフラグは1つで、ロードイベントは次の書き込みと交錯します。
React は**自分が最後に書いた prop の値**と比較して属性を更新するか決めるため、
命令的な書き込みでその記録が古くなり、たまたま新しい計算結果が古い記録と一致すると
**更新をスキップ**します。その時点で属性に入っていたのが 2 の空文書なら、空のまま残ります。

いまは **書き手はエフェクト1つだけ**（`srcDoc` prop は削除）で、ナビゲーション検知は
イベントの数え上げではなく**内容比較**です。内容は DOM の事実で、イベント数は履歴についての推測です。
`device` を依存に入れているのは、デスクトップとデバイス枠が**別の `<iframe>` 要素**だからです
（切り替えると空の iframe が新しくマウントされ、他に誰も気づきません）。

実測（ログインできないためコンポーネントを直接駆動）:

```
プロジェクト読み込み 15回  → 15回描画・白紙0・中央値103ms
デバイス切替             → 切替ごとに描画1回、属性も正
コードタブ表示中に読み込み → 8/8 が非表示のまま描画完了（display:none でも遅延しない）
```

元の間欠的な失敗そのものは**再現できていません**。直したのは仕組み（3者書き込み＋
イベント数え上げ）であって、特定の1事象ではありません。

### バージョン選択はチャットを書き換えない

右上のバージョン選択は、**キャンバスの表示を切り替えるだけ**です。

> **本文は個別に取りに行きます。** `GET /versions` はメタデータのみを返す設計（本文は S3、
> 一覧で返すと1行ごとにダウンロードが発生する）なので、`entry.html` は常に空文字です。
> ドロップダウンはそれをそのまま表示に渡していたため、**バージョンを切り替えるたびに
> プレビューとコードが真っ白**になっていました。いまは `GET /versions/:id` で本文を取得します。
> 取得に失敗したときは選択を元に戻してキャンバスには触れません — 前の文書を出すのは誤りですが、
> 空にするのはもっと悪く、データが消えたように見えます。
>
> **「現在の状態」という行は削除しました。** 最新バージョンと同じものだったからです。文書を
> 変える経路はすべてバージョンを書きます — 生成、チャット編集、そして `POST /versions` を通る
> 直接編集。両方を並べるメニューは「この2つは何が違うのか」を訊かせますが、答えは「何も」でした。
>
> ただし1箇所だけ同義ではなく、そのままでは消せませんでした。**直接編集の保存はバージョンを
> 書いて誰にも知らせていなかった**ので、一覧は編集前の文書で終わったままでした — つまり画面に
> 出ているものへ戻る道が「現在の状態」だけで、それが別物に見えていた原因そのものです。保存時に
> 一覧を更新するようにしてから消しています。同一性を仮定するのではなく、アプリが維持する形に
> してから。
>
> 副産物として、バージョン比較が**同じ文書同士**で開かなくなりました。左が最新版・右が現在の
> 状態だったので、開いた瞬間「変更なし」でした。今は最後の実行とその1つ前で開きます。

以前はバージョン記録からチャットを再構築していました。バージョンが持っているのはプロンプトと
スコアだけなので、**すべての応答が「UI generated」に潰れ、モデルの推論が消えていました**。しかも
チャット履歴はその状態で保存されるため、取り消しがききません。過去のバージョンを見る操作は
会話への編集ではないので、そう振る舞わないようにしました。

> 既に潰れてしまった会話は復元できません。バージョン記録に推論が入っていないためです。

### バージョン比較（VersionDiff）

プレビュー上部の、バージョン選択の**隣**にあります。設定ドロワーの中ではありません — 比較を開くと
そのドロワーが閉じ、**ドロワーがこのコンポーネントを描画していた**ので、オーバーレイは生まれた
コミットと同じコミットで破棄されていました。**自分の入れ物を閉じるコントロールは、その中には置けません。**

全画面のオーバーレイですが、**アプリのヘッダは残します**。消すとプロジェクト一覧への戻り道と
アカウントメニューが失われ、このアプリの中の一画面ではなく別のアプリに見えます。高さは書き写さず
**実測**します（ヘッダはスタイルシート上で高さを持たず、中身のまわりの padding なので、数値を書けば
中身が変わった瞬間に古くなるコピーになります）。

**左右それぞれでバージョンを選べます。** 以前は左が保存済みバージョン、右が常に現在の文書という
非対称で、**2つの保存済みバージョンを比べることが表現できませんでした** — 回帰が数回前のときに
まさに必要になるのに。

**画面タブは実行フレーム**（`LiveFrame`）です。サムネイルではありません — 一覧画面はどのバージョンでも
同じに見え、**変わった詳細画面を開くまで違いが出ない**からです。1:1でクリックでき、「画面を連動」で
片方の遷移をもう片方に伝えます（生成物はハッシュルーティングが契約なので、フレームの中に手を
入れずに現在の画面が読めて、設定もできます。フレームは `allow-same-origin` なしのサンドボックスで、
`postMessage` が唯一の経路です）。

**コードタブはファイル単位の差分**です。生成物は1つの転送文書の中に入った複数ファイルなので、
1本の長いテキストとして比較すると「1400行目あたりの変更」に見えます。分割してから照合すると
「`src/screens/Detail.tsx` +18 −6、ほかは無変更」になります。分割は速くもなります — 照合は O(n·m) で、
**個々の積の和は和の積より小さい**（変わっていないファイルはその前に文字列比較で落ちます）。

- 変更のないファイルは一覧に出ません。変更点の一覧は、それが変更点の一覧であるときだけ役に立つので
- 各ファイルの見出しは**本文がスクロールして通り過ぎる間その場に留まります**
- 省略された連続行のマーカーが**再開する行番号を両バージョン分**持ちます（`@@ -18 +18 @@ 17 行省略`）
- 2カラムは `minmax(0, 1fr)` ×2 と折り返し。以前は `max-content` で、**長い1行があるだけで右の
  バージョンが画面の外**に運び出されていました — 2つを並べることだけが目的の画面で
- 打ち切りは**行のペアを作った後**。照合の出力順は「削除の並び → 追加の並び」なので、先に切ると
  400行の削除だけが出て、編集ではなく空にされている絵になります

### 判別できなかった形式は、React を名乗らない

`detectKind` は `.tsx` / `.vue` / `.svelte` を探し、どれでもなければ `null` を返します。`?? 'react'` が
それを選択に変え、`disabled={!!displayHtml}` が凍結していました — **推測が事実として表示され、その上で
変更不能**に。次の編集は React として送られ、中身は React ではないマークアップです。

いまは検出が失敗したことを覚えています。**判別できていない形式はロックしません** — ロックは編集を
プロジェクトに揃えるためのもので、形式が不明なら揃える相手がいないので。HTML 期のプロジェクトが
残っているため、これは逆生成の削除とは独立に必要でした。

### プレビューのデバイス表示

Desktop / Tablet / Mobile は幅の切り替えではなく**デバイスの枠ごと差し替え**ます。

| | 見た目 | 画面サイズ |
|---|---|---|
| Desktop | macOS のウィンドウ（信号機ボタン + URLバー） | 可変 |
| Tablet | iPad（角丸34px・ホームインジケータ） | 820 × 1180 |
| Mobile | iPhone（角丸54px・Dynamic Island・ホームインジケータ） | 393 × 852 |

**枠の外側にベゼル分を足しています。** ベゼルを幅の内側に取ると、iPhone 表示の実効ビューポートが
393 ではなく 371 になります。その 22px は `max-width: 393px` のブレークポイントが発火するか
どうかを決める幅であり、「実機と同じ幅で確認する」という目的そのものを壊します。実測で
`.preview__device-screen` が 393 / 820 ちょうどになることを確認しています。

#### 縮めるのではなく、縮小して収める

枠には `max-width: 100%` が付いていました。プレビュー枠はチャットと画面を分け合うので
**デバイスより狭いのが通常**です。そこで枠が縮み、iframe も一緒に縮みました。

結果、「Tablet」は**あるモニタでは 640px、別のモニタでは 780px** を意味し、
`max-width: 768px` のブレークポイントは**ユーザーのウィンドウ幅次第で**発火したりしなかったり
します。これが「タブレットとモバイルで UI が乱れる」の中身です — **ビューポートが一度も
デバイスのものではありませんでした**。

現在は枠が実寸を保ち、`transform: scale()` で全体を縮小します。transform はレイアウトに
影響しないので、**iframe の中のページは何倍に縮小されていても 393 / 820 CSS px を見ます**。
倍率は `ResizeObserver` が枠の実測から求め、1 を超えません（実物より大きい端末はモックに
見えるため）。

実測で確認済み — プレビュー枠を 1000 / 520 / 340px と変えても、中のページが見る幅は
**常に 393px** のままでした。

#### 実機に寄せた点（P7）

| | 実機の値 | 実装 |
|---|---|---|
| iPhone 本体角丸 | 約 55-56px | `56px` |
| Dynamic Island | 125 × 36pt | `125 × 36` |
| ホームインジケータ | 140 × 5pt | `140 × 5` |
| iPad 画面角丸 | 約 18px | `18px` |

側面ハードウェア（消音スイッチ・音量± ・電源、iPad は上面電源とフロントカメラ）を
描き足しています。シルエットが「角丸長方形」ではなく端末として読めるようにするためで、
本体色もフラットな単色からエッジにハイライトの入るグラデーションにしました。

Dynamic Island とホームインジケータは描いていますが、**時刻や電波表示は作っていません**。
架空の時刻は生成物自身が持つ UI と紛らわしく、モックの一部と誤読されるためです。

### 返信のプレビュー画像

各アシスタント返信の下に、その回で作られた画面のサムネイルが出ます。**2つの理由で常に空白でした。**

1. `<iframe srcDoc={msg.html} sandbox="">` — sandbox 空文字はスクリプトを含む全機能を無効化します。
   このアプリの生成物は、HTML モックなら `.screen{display:none}` をルーターが解除して初めて描画され、
   React ならソースブロックと空の `<div id="root">` しかありません。**どちらもスクリプト無しでは白紙です。**
2. チャット履歴は DynamoDB の 400KB 上限があるため文書を保存できず、再読込のたびに `html` が落ちていました。

1 は `ProjectThumbnail` に置き換えて解決しています（静的モックは第一画面を強制表示する CSS を足し、
React はコンパイルしてから `sandbox="allow-scripts"` で描画する、という処理を元から持っています）。

2 はバージョン履歴から復元します。generate も modify も必ず1バージョンを書くので文書はそこにあり、
**添字ではなく時刻で突き合わせます** — エラー返信・却下された編集・プラン提案にはバージョンが無く、
位置がずれるためです。窓は120秒で、それを超えたら付けません（無関係な文書がエラー返信に付くよりまし）。

> なお両者の fetch は競合し、多くの場合バージョンが先に返ります。復元エフェクトを `versions` だけに
> 依存させると空のスレッドに対して1度走って終わりになるため、`messages.length` も依存に入れています。

### Undo / Redo の削除

ヘッダーの Undo / Redo と、それを支えていたメモリ上の文書スタックを削除しました。バージョン履歴が
永続的な記録として同じ役割を果たしており、二重に持つ意味がないためです。

### プロジェクトの ZIP ダウンロード

ヘッダーの「ZIPでダウンロード」は、Code タブに出ているファイル一式（分割したソース +
スキャフォールド）をそのまま固めます。展開すればそのまま `npm install` できます。

これは **Copy HTML の置き換え**です。React 出力に対する Copy HTML は実害がありました —
クリップボードに入るのは `data-file` ブロックを詰めた転送用の1文書で、**何かの HTML でもなければ
開けるプロジェクトでもない**ものだったためです。

ZIP の生成は `utils/zip.ts` に自前で持っています（stored、無圧縮）。必要なのは「テキストを
数十個まとめて OS が開ける書庫にする」ことだけで、そのために依存とバンドルを増やす釣り合いが
取れないためです。Windows の Expand-Archive で展開し、UTF-8 のファイル名と日本語の内容が
保たれることを確認しています。

### 認証画面の入力（半角固定）

ログイン・パスワード設定・MFA の各入力は、`utils/halfWidth.ts` で**入力のたびに半角へ変換**します。

日本語IMEが有効なままだと、ａ と a、７ と 7 のように画面上ほぼ見分けの付かない全角文字が入ります。
Cognito はバイト列で比較するので単に失敗し、ユーザーは正しく見えるフィールドを読み返し続けることに
なります。**後から検証するより、起き得なくする方が説明することが無くて良い**という判断です。

全角ASCIIは U+FF01–U+FF5E が U+0021–U+007E と同順なので固定オフセットで変換し、全角スペースは
半角に、それ以外の非ASCII（かな・漢字・絵文字）は破棄します。MFA は加えて数字のみ・6桁で切ります
（`maxlength` は打鍵と貼り付けしか縛らず、オートフィルは素通りするため）。

### 停止と再アタッチ

| 操作 | 挙動 |
|------|------|
| 停止ボタン（入力欄） | クライアント側のポーリングを止める。**サーバ側のジョブは走り続ける** |
| プロジェクト一覧へ戻って再入場 | `activeJob.ts` が localStorage に保存した jobId から `resume(jobId)` でポーリングを再開し、チャットと進捗を復元する |

## 入力欄のコントロール

### 添付（クリップボタン）

クリップは1つで、拡張子で振り分けます（`utils/dataAttachment.ts`）。

- **画像**（png / jpg / gif / webp、1枚5MB・最大8枚）: 1枚目は `image`、2枚目以降は `extraImages` に入り、
  各画像に説明欄が付きます。送信時は `uiImagesForSend` が「1枚なら `image`、2枚以上なら `images`」を決め、
  `captionsForSend` が説明を揃えます（2枚以上なら位置を合わせた配列、1枚なら説明だけ）。
  **生成・編集・プラン・プラン承認後のビルドのすべてが、同じ2つの関数を通して送ります**（2026-09-14 まで、
  編集とプラン承認後は1枚目しか送らず、1枚だけのときの説明は送っていませんでした）
- **データ・資料**（csv / tsv / json / md / txt / pdf、1つ）: テキストで読み、PDF はブラウザで文字を取り出してから送ります。
  チップには行数・件数・ページ数を出します
- **送る前に断るもの**（`utils/requestLimits.ts`）: 2,000文字を超える依頼文、5MB を超える画像、9枚目以降の画像、
  512KB を超えるデータファイル。値は API と同じで、`backend/test/client-limits.test.mjs` が一致を確かめます

添付は送信したメッセージにだけ使い、送信後にクリアします。プランモードだけは、承認してビルドが走るまで保持します。

### プルダウン

入力欄は**内容に応じて高さが伸びます**（最大220px。CSS の `max-height` と JS の上限は必ず一致させること — 片方だけ低いと、伸ばした直後に無言で切り詰められます）。

モデル・デザインプリセット・出力形式は**プルダウン**です。以前はチップの3列でしたが、チップに入るのは単語ひとつで、当時のプリセット名（「editorial」など）が何を指すのかに答えられませんでした。プルダウンなら各項目に説明を添えられます。

| プルダウン | 表示例 | 説明として出るもの |
|-----------|--------|-------------------|
| モード | 構築 | そのままUIを生成します |
| モデル | Sonnet 4.6 | 速度と品質のバランス。通常はこれ（モードによるロックはありません） |
| デザイン | Carbon（IBM） | 業務システム・データの多い管理画面 / 角丸なし・グレーの階層・ブルー #0F62FE |
| 形式 | React | プロジェクトの出力形式。文書があるあいだはロック（「形式を変更」で外れる） |

バージョン表記は `GET /models` が Parameter Store から取得した実際のモデル ID から抽出するため、モデルを差し替えてもフロントの再デプロイは不要です。

`Dropdown` は `<select>` ではなく自作です。ネイティブの select は説明行を持てず、周囲のカプセルに合わせた見た目にもできないためです。外側クリックと Escape で閉じ、矢印キーで項目を移動します。メニューはビューポート基準で配置し、スクロール領域の端で見切れないようにしています。

**プロンプトの添削.** 入力欄の「添削」ボタンは、入力中の依頼文を `POST /refine-prompt`（Haiku）に送り、
「添削案」として表示します。添削は、生成するモデルが迷うところだけを6点で埋めます —
画面の一覧（5つ以上）、各画面に何が並ぶか、共有する状態とそれを書き換える操作、空・読み込み中・エラーの状態、
扱うデータの性格（件数や値の幅）、この製品を一般的なものと違わせる決まりごと（2〜3個）。
**見た目（色・フォント・余白など）や技術スタック、依頼に無い機能は足しません**（デザインは生成側の仕事のため）。

## React プロジェクトのプレビュー（reactPreview.ts）

生成物が `<script type="text/jsx" data-file="...">` ブロック群の場合、バンドラを使わずブラウザ内で実行します。

```text
data-file ブロック群
   ↓ virtualFs.ts    仮想ファイルシステムを構築
   ↓ transformsFor() 拡張子ごとに変換設定を決定
   ↓ Sucrase         TypeScript / JSX を変換
   ↓ resolve()       import をモジュールレジストリで解決
   ↓ React ランタイム  Vite の仮想モジュールとして同梱（esbuild で1つの IIFE に）
```

**拡張子ごとの変換**: `.ts` に `jsx` トランスフォームを有効にすると `useRef<Route[]>` のようなジェネリクスが JSX として解釈されて失敗します。`.tsx` のみ jsx を有効にし、`.ts` は typescript のみとします（失敗時は `.tsx` として再試行し、警告を出します）。

**import 解決**: モデルが `../imports/icons` のように階層を1つ間違えることがあります。`resolve()` は完全一致で見つからない場合に末尾一致でフォールバックします。それでも解決できない import は、空オブジェクトではなく**例外を投げるスタブ**に置き換えます（空オブジェクトだと画面が真っ白になるだけで原因が分かりません）。

## プレビューがフレームの外に出ないようにする（previewGuard.ts）

プレビューは `sandbox="allow-scripts"` の iframe に `srcdoc` で流し込みます。ここから**出ていかせない**のが previewGuard の仕事です。出ていくと `dxxxxxxxxxxxxx.cloudfront.net で接続が拒否されました` のような画面になり、プレビューでの操作ができなくなります。

### 原因1: ハッシュリンクが「別ページ」になる

これが報告された不具合の本体です。

srcdoc 文書の**URL は `about:srcdoc`** ですが、**base URL はホストページから継承**されます。そのためブラウザは `href="#/cart"` をホスト側に対して解決し、`https://<ホスト>/#/cart` は `about:srcdoc` とは別文書だと判断して**フル遷移**します。実測すると `beforeunload` が発火し、iframe の `load` が発火し、フレームは応答しなくなります。

生成されるアプリは**すべてハッシュでルーティング**します（`useNavigation` が `#/list` `#/detail/42` を吐きます）。つまり**画面遷移のリンクすべてがこれを踏んでいました**。

対処は、ガードが自分で実行することです。`location.hash` への代入は文書自身の URL（`about:srcdoc`）に対する操作なので、同一文書のフラグメント変更のままで、`hashchange` も普通に発火します。

| 実測（実ブラウザ、sandbox 付き iframe） | 修正前 | 修正後 |
|---|---|---|
| `<a href="#/cart">` | フレームが死ぬ | 生存、`about:srcdoc#/cart`、`hashchange` 発火 |
| `<a href="/contact">` | ブロック | ブロック（トースト表示） |
| `<a href="//localhost:3000/x">` | ブロック | ブロック |
| `<form action="/search">` | ブロック | ブロック |
| `window.open()` | ブロック | ブロック |
| `location.href = '/contact'` | **すり抜け** | すり抜け（→ ウォッチドッグが復帰） |
| `location.assign` / `replace` | **すり抜け** | すり抜け（→ 同上） |

### 原因2: 「守っているように見えて何もしていない」コード

ガードには `Location.prototype.href` を再定義し `assign`/`replace`/`reload` を潰すコードが try/catch 付きで入っていました。**どれも効いていません。** これらは location オブジェクトの `[LegacyUnforgeable]` な own プロパティなので、prototype 側のディスクリプタ取得は `undefined` を返し、代入は黙って失敗します。catch がその証拠を飲み込んでいました。

中から防げないものは、外から**復帰**させます。削除して、Preview.tsx のウォッチドッグに委ねました。

### ウォッチドッグ（Preview.tsx）

フレームは opaque origin なので `contentWindow.location` は読めません。**訊きます。** `load` のたびに ping を送り、ガードが pong を返さなければ、そこにあるのは私たちの文書ではないので `srcdoc` を書き戻します。

これも一度間違えています。最初は「ガードが起動時に1回 alive を送り、ホストは load でフラグをクリアする」形にしましたが、**ガードは文書のパース中に走り、`load` はその後に発火する**ので、答えが先に届いてから捨てられていました。実測では正常なロードのたびに「遷移した」と誤判定し、リトライ回数（3回）をユーザーが何かする前に使い切っていました。**問いは順序を自分で持ちますが、フラグは持ちません。**

> 以前ここにあった復帰処理は `srcdoc` 属性を前回書いた値と比較していました。これは一度も発火しません — **フレームが遷移しても `srcdoc` 属性は変わらない**からです。属性には私たちの文書が入ったまま、中身だけがホストサイトになっていました。

ガードを使わない文書（コンパイル中の空ページ、ビルドエラー画面）は pong を返せないので、書き込んだ文書に `makeui-nav-block` が含まれるかを見て、含まれないときはウォッチドッグを止めます（さもないと永久に書き戻します）。

### 未生成画面のリンクには、そう言う

内部リンクの遷移先が見つからないとき、以前は黙ってキャンセルするだけでした。外から見ると壊れたボタンと区別がつきません。「この画面はまだ作られていません」と出します。

`classifyHref()` だけは純粋関数として切り出し、`String(fn)` でガードに埋め込んでいます（テスト対象と出荷物が同一になります）。それ以外はブラウザでしか測れないため、実ブラウザでの計測に頼っています。

### 「New Chat」は3つのことをしていて、そのうち1つは会話を消していた

キャンバスを消し、出力形式のロックを外し、メッセージ一覧を空にしていました。**メッセージ一覧は
保存されている**ので、最後のひとつはプロジェクトの会話をサーバーから削除します。名前に出ていた
のはそのうち1つで、破壊的な方は出ていませんでした。

押されていた理由は形式です。形式のプルダウンは文書があるあいだロックされ（編集はプロジェクトが
書かれているフレームワークで送らないと壊れる）、その鍵を外す唯一の道がこれでした。

いまは **「形式を変更」** で、それだけをします。**フラグを立てるだけで、何も消しません** —
次のメッセージが編集ではなく生成になる、というフラグです。会話も、バージョンも、記録も、画面の
文書も残り、新しい文書ができたときに置き換わります。もう一度押せば解除なので、確認ダイアログは
ありません。確認するものがないので。

- 文書があるときだけ出ます。キャンバスが空なら形式のプルダウンはもともと動くので、かかっていない鍵のためのボタンは雑音です
- オン状態は塗り・チェックマーク・`aria-pressed` で示します。印のないモードは、驚かされて初めて気づくモードです
- ラベルは両状態とも「形式を変更」。一時期オン側を「新規作成にする（解除）」としていましたが、**ラベルと括弧が正反対のことを言っていました** — 1つのチップに状態と操作の両方を名乗らせるとそうなります
- プラン承認も同じ判断をします。オンのときのプランは文書を渡さずに作られるので、承認時に編集として実行すると新規プロジェクト向けのプランを既存の文書に当てることになります

## iframe プレビューとナビゲーション制御

```html
<iframe sandbox="allow-scripts" />
```

`allow-same-origin` は付与しません。生成物の `<head>` 直後に **`PREVIEW_GUARD_SCRIPT`（previewGuard.ts）** を挿入します。

| リンク種別 | 動作 |
|-----------|------|
| `href="#"`, `href="#section-id"` | そのまま通過（スクロール・画面遷移） |
| `href="#/route"` | ハッシュルーターが処理 |
| `href="https://..."` | ブロック → 「外部リンク（デモ環境では無効）」トースト |
| `href="/relative/path"` | スマートナビゲーション（下記） |
| `javascript:void(0)` 等 | そのまま通過 |

**スマートナビゲーションのフォールバックチェーン**
1. `id="view-{slug}"` + `window.showView(slug)`
2. `[data-view="{slug}"]` のクリックイベント
3. `id="{slug}"` の `scrollIntoView`
4. いずれも失敗 → 何もしない

**onclick の保全**: `stopImmediatePropagation()` は呼びません。外部 URL のみ `preventDefault()` でキャンセルし、内部ナビゲーションには一切干渉しません。

**フォーム送信**: `submit` をキャプチャして `preventDefault()` + 「送信しました（デモ）」トースト。

**Location のオーバーライド**: `location.href = '#hash'` は許可、`'/path'` はサイレントにブロック。`assign` / `replace` / `reload` は noop。

### 利用可能モデル — プルダウンからチェックボックスへ

各モデルを独立してONとOFFにします。

以前は上限（＝天井）をひとつ選ぶ4択のプルダウンで、Haiku / Haiku+Sonnet / … と**入れ子になる権限しか表現できません**でした。「品質の下限を上げたいので Opus だけ許可し Haiku は禁止」は、この形では言えない文です。チェックボックスなら言えるので、解決側（`decideTier`）もラダーではなく集合を受け取るよう書き直しました。

| 設定 | 旧プルダウン | 新チェックボックス |
|------|------------|-----------------|
| Haiku まで | ✅ | ✅ |
| Haiku, Sonnet | ✅ | ✅ |
| Opus だけ | ❌ 表現不可 | ✅ |
| Haiku と Opus（Sonnet 抜き） | ❌ 表現不可 | ✅ |
| 自動だけ許可 | ❌ | ❌（自動はモデルではないため、実モデルが最低1つ必要） |

- **許可されていないモデルを要求したときは、まず下に落ちます。** 引っ込められたモデルが「格上げ」になってはいけないからです。下に何も許可がないときだけ上を選びます（Opus だけ許可のユーザーが Haiku を要求したら Opus。動かないより高くつくほうがまだよい）。
- **`auto` は集合の要素です。** モデルではなく「選ぶという決定」であり、その結果が Opus になり得るため、Opus を許可することと `auto` を許可することは別の権限のままです。`auto` が許可されていなければ分類器は呼びません（どのモデルを使うかモデルに訊いて、その答えを上書きするのは何も買わない呼び出しです）。
- **最後の1つは外せません。** 空集合はサーバーが 400 で拒否します。実モデルを含まない集合は解決できず、解決器のフォールバックは「設定を無視する」なので、うっかりの空集合が**全許可**になってしまいます。チェックを外す操作の意図の正反対です。最後のボックスを disabled にすることで、クリックする前にそう言います。
- 保存済みの旧ラダー値は**読み出し時に集合へ展開**します（`opus` → `haiku, sonnet, opus`）。全ユーザーの設定を書き換える移行は途中で止まり得ますが、読み出し時の展開は止まりません。

## 転送形式の移行で取り残されていた3つ

行フェンス（`@@@makeui:file`）への移行時、フロントエンドの述語が3つ、
`data-file` を見たままになっていました。3つとも**現在生成されるすべての
プロジェクトで false になり**、それぞれ別の機能を静かに壊していました。

### コードエディタが1ファイルも保存できなかった（`sourceEdit.ts`）

`blockOf()` が `<script|style data-file=…>` しか知らず、`editability()` と
`applyFileEdit()` の**両方がこれを土台に**していました。結果として、
行フェンス移行後に生成されたすべてのプロジェクトで、ツリー上の全ファイルが
「このファイルは保存対象に含まれていません」と表示され、保存は `null` を
返していました。機能まるごとが、現行のすべての文書に対して死んでいたことになります。

すぐ上の `isProject()` は同じ理由で既に修正済みでした。**同じ問いに2つの綴りを持つと、
こうして片方だけが取り残されます。**

フェンスの探索は正規表現ではなく行単位です。フェンスは行全体であり、ファイルの中身には
何でも入り得る（フェンスの接頭辞で始まる行を含めて）ため、行そのものと一致させるのが
中身に騙されない唯一の方法です。オフセットは元の文字列上で返すので、呼び出し側は
文書を組み直さずに差し替えられます（組み直すと他の全ファイルの改行が変わります）。

### CSS インスペクタが何もしなかった（`directEdit.ts`）

スタイルの手編集は `<style data-file="styles/overrides.css">` ブロックとして
文書に注入されていました。プロジェクトのプレビューはファイル群からコンパイルされ、
そのブロックはファイルではありません。実測: ブロック注入の前後で
`splitHtmlToFiles` が返すファイル数は**3のまま**でした。

つまりユーザは値を動かし、「保存しました」と表示され、プレビューは変わりません。

手編集は生成 CSS と区別できる必要があります（`readOverrides()` が「ユーザが何を
変えたか」を答えるため）。そこで、プロジェクトの場合は**スタイルシート末尾の
マーカー付き領域**に書きます。最後のスタイルシートの最後という位置は、
オーバーライドブロックが持っていたカスケード上の位置と同じです。

### テキスト編集が、動かないどころかファイルを壊し得た

`isReactDocument()` も `data-file` ベースで、これが**テキスト編集の門番**でした。
テキスト編集は単一ページ専用です — プロジェクトのテキストは `.tsx` / `.vue` /
`.svelte` にあり、描画された DOM から戻る正直な経路がありません。

門番が false のまま全プロジェクトで開放されており、`applyTextEdit()` は文書全体を
`DOMParser` で解析して再直列化します。フェンス付きプロジェクトのソースは `<body>` 内の
テキストなので、**1往復ですべてのソースファイルの `<button …>` が
`&lt;button …&gt;` になります**。何も起きないのではなく、壊れます。

現在は両方の転送形式を、`splitHtmlToFiles` ではなく正規表現で判定します。
旧形式の読み取りには `DOMParser` が必要で、**文書破壊に対する門番が
パーサの存在に依存すべきではない**ためです。

## バックエンドとフロントエンドで、コンパイラは2つあります

生成物は別々のコードで2回コンパイルされます。

| | 役割 |
|---|---|
| `backend/src/tools/framework-compile.ts` | パイプラインが検証に使う。「ビルドできるか」を決め、採点の前提になる |
| `frontend/src/utils/frameworkCompile.ts` | ユーザのプレビューが実際に走らせる |

意図的に並行に保たれていますが、**別々のファイル**です。食い違えば、この製品で
最悪の形の失敗になります — バックエンドは健全と判定し、スコアは高く出て、
ジョブは成功を報告し、ユーザは真っ白な画面を開く。どちらも内部的には一貫しているので、
どちらの側も気づきません。

`backend/test/compiler-parity.test.mjs` が両方を同じ入力に通して比較します。
実測9実行・192ファイルで食い違いゼロでした。

> **ただし一致は正しさではありません。** Sucrase のクラスフィールド降格が有効な
> Svelte を壊していた件は、**両方がまったく同じように間違っていた**ため、
> この一致テストを素通りしました。それでもこのテストには価値があります
> — 一致が崩れる形の失敗を捕まえるのが目的だからです。

## プロンプトテンプレートを長くしている理由

`PromptTemplates.tsx` の各項目は、1文の説明から**4〜6画面ぶんのブリーフ**へ書き換えてあります。
以前は「ECサイトのトップページ。ヒーローバナー、商品カード4つ、カテゴリナビ、フッター付き。」
のような一文で、これは**絵の説明**です。

パイプラインはまったく別のものを前提に組まれています。画面と情報構造を決める設計フェーズ、
コントロールを1つずつ列挙してそれぞれが書き込む状態まで書き出すインタラクション設計、
その仕様に対して実装するビルド、そして依頼文から抜き出した要件を完成物で照合する工程。
静的な1ページを渡すと、この機構のほとんどは仕事がなく、薄いブリーフからは薄い出力が出ます。

そこで各テンプレートは、設計フェーズが実際に必要とするものを名指しします:

- ドメインを具体的に（視覚言語はここから決まります）
- 4〜6画面と、それぞれの目的
- アプリが持つ状態と、それを書き換えるアクション
- データの形（モックのレコードが「らしく」なります）
- どの画面からどの画面へ行けるか（到達不能な画面を防ぎます）
- 空・処理中・失敗の状態と、画面に出す具体的な文言（要件として照合できます）

2026-09-12 に全テンプレートをこの形に書き直し、「プロンプトの添削」（`POST /refine-prompt`）も
画面・中身・状態・データ・決まりごとの観点で具体化するようにしました。テンプレートは `src/data/promptTemplates.ts` にあります。

**長いのは意図です。** テンプレートは「この製品へのブリーフはこう書く」を利用者に見せる
唯一の場所なので、薄い例は薄い書き方を教えてしまいます。
